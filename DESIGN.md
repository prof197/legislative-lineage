# Design

Legislative Lineage takes one state bill and finds bills in other states that carry a similar provision. For each match it shows where the bill was introduced, what happened to it, and how its text differs. It indexes every state bill from the 2023–2026 sessions on a single laptop, matches them section by section in two stages that need no API key, and publishes the results for one state as a static site.

Sections marked **To be measured** fill in as the build reaches them. Every number here names the command and the committed output it comes from.

## Problem

Model legislation spreads by copying. An interest group, a uniform-law body or another state's statute supplies text, and a legislature introduces it, sometimes verbatim and sometimes with changes that matter: a narrowed definition, or a dropped enforcement clause. Nothing on a bill's face says where its text came from, so anyone who wants to know where else a provision appeared has to search for it.

Three properties of the corpus make this hard:

- **Size.** Every bill from all 50 states over four years. Comparing every pair of sections is quadratic: *N* sections make *N*(*N* − 1)/2 pairs, so the method has to find candidates without enumerating pairs. The snapshot has *N* = 3,182,343 sections (`uv run lineage stats`, `reports/coverage.json`), which is about 5.1 × 10¹² pairs.
- **The unit is the section, not the bill.** A copied provision often sits inside a much larger bill, such as a code revision or a budget. Similarity between whole bills dilutes it below any useful threshold.
- **Copying is not always verbatim.** Reordered clauses and substituted terms break exact-text methods, while generic legal phrasing ("the department shall…") makes meaning-based methods over-match.

The tool reports shared text and timing. It does not claim who wrote a bill, or which of two similar bills came first in any causal sense.

## Constraints

| Constraint | Consequence for the design |
|---|---|
| Retrieval needs no API key | Both matching stages run locally: hashing, then a local embedding model. A model is called only to write the change explanations, and those replies are cached so a keyless run can replay them. |
| Hosted output is static | All results are precomputed. The site serves JSON files and has no query server or hosted vector database. |
| Runs on one laptop | Data structures must fit in memory or stream from disk. Hot loops are vectorized or run in compiled code, never per-element Python. |
| Queries run offline | `lineage query` runs on a user's laptop after one download of the prebuilt index, published as [release assets](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas) of under 2 GiB each. The index must be files that memory-map, not a structure rebuilt in memory on each run. |
| Reproducible | The data snapshot date is pinned, dependencies are locked in `uv.lock`, and random seeds are fixed. |
| Redistributable data | Bill text comes from [Open States](https://open.pluralpolicy.com/data/) bulk data, which is dedicated to the public domain. Legislators' official work is not copyrightable ([*Georgia v. Public.Resource.Org*, 2020](https://www.supremecourt.gov/opinions/19pdf/18-1150_7m58.pdf)). |
| Explanations are grounded | Every change an explanation claims must cite an aligned span that exists, and code checks this. A claim that fails the check is dropped. |

## Pipeline overview

```
Open States snapshot ─► ingest ─► text layer ─► sections ─┬─► near-duplicate stage (MinHash + LSH) ─┐
   (pinned JSON)       (DuckDB)  (fetch,       (split,    │                                          ├─► merge ─► bill scoring ─► alignment ─► explanations ─► export
                                  merge)       normalize, └─► semantic stage (embeddings + ANN) ─────┘                              (difflib)    (only model call,  (static JSON)
                                               boilerplate)                                                                                       cached)
```

1. **Ingest.** Verify the raw archives against the committed manifest, then read the per-session JSON into Parquet tables without editing the raw files ([DR-4](#dr-4)). See [Data snapshot](#data-snapshot).
2. **Text layer.** Where the export's text is unusable, fetch the bill's latest version from the legislature and extract it, then choose each record's text, fetched or exported, into one table that every later stage reads ([DR-6](#dr-6)). See [Text layer](#text-layer).
3. **Sections.** Restrict matching to the document types that can carry law ([DR-5](#dr-5)), then split each bill on its section headings, falling back to fixed paragraph windows. Normalize the text and flag legal boilerplate such as enacting clauses, severability and effective dates, which would otherwise dominate the matches.
4. **Near-duplicate stage.** Long sections are cut into overlapping windows of comparable size ([Windows](#windows)). Word shingles, MinHash signatures and LSH banding generate candidate pairs of windows that share text, each candidate is verified against its full signature ([DR-3](#dr-3)), and a section pair matches when any of its windows do.
5. **Semantic stage.** A local sentence-embedding model and an approximate nearest-neighbor index generate candidates that share meaning but not wording. This is a second candidate generator over every section, not a reranker of the first stage's output, so it can find pairs the first stage never proposed.
6. **Merge and score.** Each match records which stage found it. A bill's score against another bill is the share of the *query* bill's text that falls in matched sections, so a provision inside a large omnibus still scores high.
7. **Alignment.** Word-level alignment marks the spans that were copied exactly, the spans that were paraphrased, and the unmatched text.
8. **Explanations.** For featured matches, a model summarizes what changed, citing span ids. The citations are validated in code.
9. **Export.** Per-bill and per-story JSON for the static site ([DR-1](#dr-1), [DR-2](#dr-2)).

## Data snapshot

**Source.** Open States publishes one JSON archive per state legislative session ([Session JSON Archives](https://open.pluralpolicy.com/data/session-json/)). The corpus is every archive for the 50 states whose session overlaps 2023–2026. Each archive holds a README and one file of bill records, and each record carries at most one extracted text (`raw_text`) together with the URL it came from.

**As-of dates.** The archives are generated independently, so the snapshot has no single date. Each archive's README states when it was generated, and that *Generated At* timestamp is the as-of date of its records everywhere: in the tables, the reports and the site's data stamp. The listing page also shows an "updated" date for each archive. It does not match Generated At, so it isn't used.

**Pinning.** `snapshot/manifest.json` (committed) lists every archive with its size, SHA-256 and Generated At. Ingest refuses to run if the files on disk differ from the manifest in any way: a changed file, a missing one, or an extra one. A rebuild therefore either reproduces the same inputs or fails loudly.

**Rebuilding the raw files.** `lineage fetch-raw` downloads every pinned archive that is missing locally. Open States serves them publicly, with no account or key. A file is kept only if its SHA-256 matches the manifest. `--repin` is the deliberate way to move the snapshot forward: it keeps the changed file and writes its new hash and Generated At to the manifest, so the change shows up in review as a diff of `snapshot/manifest.json`. Requests go out one at a time, a second apart, under a User-Agent that names the project.

**Session dates.** Bill status needs to know whether a session has ended, and the export has no session dates. `snapshot/sessions.csv` (committed) holds each snapshot session's start and end dates, read from the session lists in Open States' own scraper repository at a pinned commit, which the file's header names. `lineage sessions --commit <sha>` regenerates it. The command parses those Python modules as source and never imports or runs them, and it keeps only names and dates, not code. Some legislatures sit for two years while Open States publishes each year separately, and their bills carry over from the first year to the second. For those, the CSV names the session a bill carries over to, so a first-year bill stays alive until the biennium ends. Special sessions keep their own dates.

**Extraction failures.** The export has no error flag. A record whose `raw_text` is missing or blank counts as a failed extraction. Blank means no character that Python's `str.isspace()` rejects. The text layer fetches those records' text from the legislatures ([Text layer](#text-layer)). A record with neither stays in the `bills` table but cannot match anything. `lineage text inventory` counts the export's failures, and `lineage stats` the records still without text after the merge, per state and session.

## Text layer

Open States stays the source for bills, actions and the links to each bill's versions. Its stored text does not: for 145,946 of the 447,389 eligible records (32.6%) it is unusable, so the project fetches those records' text from the legislatures itself ([DR-6](#dr-6)). `lineage text inventory` measures the gap and plans the fetch (`reports/text_inventory.json`).

**What counts as unusable.** A record's stored text is unusable when it is missing (8,708), blank (129,633), yields no section (1,389, mostly Texas's "see the PDF" notices), is a Georgia local-bill notice without the bill (774), or is an amendment stored in place of the bill (5,443, mostly Louisiana). The checks run in that order, so each record counts once.

**Which version.** The export lists every document a legislature posts for a bill among its versions: the bill as introduced, engrossed and enrolled, and also floor amendments, fiscal and impact notes, transmittal letters and dispositions. The fetch takes the latest version whose label names the bill's own text. For a passed bill that is the enrolled or chaptered text. "Latest" is read from the label first, because the exports leave most version dates empty and list versions out of order: Introduced comes before Enrolled in about half of the bills that have both, and Virginia's list runs newest first. The label's stage ranks first (introduced; then amended, substituted or unstaged; then passed a chamber or engrossed; then enrolled, chaptered or enacted), then a date (the version's, or one written in the label), then the label's number (Pennsylvania's printer's number, Utah's substitute number, New York's print letter), then the export's order. Some labels mean different things by state: Texas's "Senate Committee Report" is the bill as reported, while Utah's is the committee's letter and is skipped. Ranking by stage changed the chosen version for 60,577 of the 379,011 planned records, mostly from the introduced to the enrolled or engrossed text. An amendment names itself ("Senate Amendment 1", "HA 1 to HB 5", Nebraska's "AM123"); the bill as amended does not ("Amended Assembly", "First Engrossment with Senate Amendments"). Maryland's labels carry the bill's title after its reading, so only the reading is examined. Each fetched text records the version's label and date. Of the records without usable text, 135,732 have a bill version to fetch, 9,293 have no link at all, 918 link only amendments (911 in New Hampshire) and 4 only an unsupported format.

**Formats.** HTML is preferred where a version has it, then PDF. 60,236 of the planned records have both, 7,374 HTML only and 68,121 PDF only. Extraction keeps lines and drops markup, scripts and struck text: in a bill, struck text is current law being deleted, which is not the bill's language. PDFs are read with pypdf (BSD-3-Clause); PyMuPDF is excluded by its AGPL license. Fetched text goes through the same cleaning and splitting as exported text ([Sections](#sections)).

**Politeness.** The fetcher names itself in its User-Agent, `legislative-lineage/<version> (+https://github.com/prof197/legislative-lineage)`. Before any bill page, it reads each host's robots.txt and follows the rules that apply to that agent. A robots.txt that answers 401 or 403 bars the host and is not asked again; any other 4xx means no rules. An overload (429), a server error or no answer is temporary: robots.txt is asked again after one and then five minutes, and a host still refusing is left unfetched, with nothing stored, so a later run asks again. Every read of robots.txt is recorded with its status. Each host gets one worker and hosts run in parallel, at one request a second or the host's crawl delay if longer. That limit is kept per host in a locked file that every process shares (`lineage.pace`), so it holds for robots.txt, retries and any number of processes together. A limit kept inside each process did not: on 2026-11-06 a scratch script without a main guard had each of its extraction workers re-run the whole fetch with its own pacing, which multiplied every host's rate by the number of workers. Every run that touches the network now goes through the `lineage` CLI, never a one-off script, and the fetcher refuses to start inside a worker process. Overload and server errors are retried with backoff, and a host that fails 20 times in a row is stopped for the run. A response body is extracted in memory and dropped; the store keeps the text, its SHA-256, the URL and the version. A rerun skips what is stored and retries only network and server failures.

**What robots.txt allows.** Of 67 hosts, robots.txt blocks the planned links on three. California's answers 403 to the fetcher, so its 2,409 records are taken from the legislature's bulk download instead (below); Tennessee's and an S3 bucket's rules block 4 more. Eight hosts set crawl delays, from 3 seconds (Nebraska) to 120 (Arizona's main site). Maine's robots.txt bars a list of named AI and search crawlers and sets no rule for other agents, so it allows this project, which identifies itself as its own tool.

**Two fixes in transport.** Connecticut's, Mississippi's and Illinois's servers send their certificate without its intermediate, which browsers fetch and Python's OpenSSL does not. `src/lineage/certs/intermediates.pem` supplies the three intermediates, each with its source URL and fingerprint, and every chain must still end at a trusted root. Illinois retired `beta.ilga.gov`, which the 103rd General Assembly's links still name; the same paths are served from `ilga.gov`, and the fetcher rewrites that one host.

**Quality test.** Before any full fetch, `lineage text sample` fetches a seeded sample from the plan: about 50 documents per state and link format, up to 30 whose stored text is unusable and at least 20 that already have Open States text, 3,735 in all (`reports/text_quality.json`). Each document is judged two ways. It is *usable* when it has at least 30 words and at least half of them are real words (letters with a vowel); this is the bar fetched text must clear. It is *clean* when it splits at section headings. PDFs are read twice from the same bytes, in text order and by each word's position on the page.

**Per-state rules.** `rules/text_layer.toml` records, per state, the link formats to fetch in order of preference and how a PDF is read, and a test checks each choice against the committed report. A state is fetched when its chosen format clears the usable bar for at least 80% of its sampled documents. The format with the best clean rate is preferred, HTML when it is within 0.05 of the best PDF reading, because HTML marks struck text and a PDF's text layer does not. Reading by position recovers Iowa's, Idaho's, Maine's, Montana's and Wyoming's PDFs, which place words one at a time, and loses lines in Illinois's, Wisconsin's and Rhode Island's, so the reading is chosen per state. The clean rate is not the fetch bar: bills without section headings still match through windows ([Sections](#sections)), so New Jersey, Missouri and Connecticut are fetched although their text rarely splits at headings, in either source. Five sites wrap the bill in menus that would otherwise be kept, so the rules name each one's content element (Minnesota, New York's Assembly, Alaska, West Virginia, Virginia), and a page without that element is an extraction error rather than a page of menus.

**Comparison with Open States.** On the sampled records that have both texts, word 5-gram overlap with Open States' text first measured 0.3–0.4 in most PDF states. Three causes explain it. Margin line numbers came out glued to each line's last word, and are now stripped ([Sections](#sections)). Some legislatures print front matter that Open States drops: Oregon's digest, Wisconsin's analysis, Louisiana's digest, a Massachusetts committee's cover page. And HTML pages carried their site's menus, which the content elements now drop. Overlap penalizes text that only one side keeps, so the report also gives containment, the share of their 5-grams found in ours: its median is 0.9 or more in 35 of the 43 fetched states with records to compare. The lowest are Idaho (0.63) and Iowa (0.67), compared on the text-order reading their PDFs are not fetched with, and Massachusetts (0.74).

**Replacing Open States' text.** Fetched text replaces the export's text for records that have both only where, on the same sampled records, our clean rate exceeds theirs by at least 0.2 over at least 10 records (`rules/text_layer.toml`, `[replace]`). Today that selects Arkansas (1.00 against 0.56), Ohio (1.00 against 0.00), Oregon (1.00 against 0.80) and Washington (1.00 against 0.00). Michigan falls short on this sample (0.95 against 0.80). Replacing the export's text everywhere would refetch every record that already has text, mostly in states where the two texts agree.

**Left out.** Indiana serves its documents only through an API that needs a registered key; its links return an empty application page. Tennessee's robots.txt disallows its one planned link. New Hampshire moved its site, and links to the old host no longer resolve (every sampled one answers "No bill text is on file"), so those are disclosed as dead links while links to the new host are fetched.

**California.** California publishes its legislative database as a bulk download (`downloads.leginfo.legislature.ca.gov`), one zip per biennium, which state law places in the public domain. Each zip holds a table of bill versions and each version's text as XML. The fetch takes the latest active version of each record, by its action date and then its version number, keeps the measure and drops the digest and struck text, and holds it to the same usable bar. It downloads one biennium at a time, checks free space against the size the server declares before writing, and deletes the zip once read. Of the 2,409 records, 2,394 get usable text, 9 are short placeholder bills below the bar and 6, from a 2023 special session, are not in the download (`reports/text_fetch.json`).

**The full fetch.** `lineage text fetch` fetches every planned record its state's rule allows, and writes outcomes per state to `reports/text_fetch.json`. Of 151,426 records, 147,874 get usable text. 2,589 links answer with an HTTP error, most of them in Montana (1,647) and Kansas (393), whose exports name older URL schemes the sites no longer serve. Ohio's export named its 135th General Assembly's documents by such a scheme, and all 1,060 failed until `lineage.fetch` rewrote that scheme to the one the site serves now, the scheme its other documents already use; 1,057 then yield usable text. A record is fetched again when its link now leads elsewhere, since the store keys each fetch by the address it requested. 575 documents yield no text, mostly scanned PDFs without a text layer and encrypted PDFs, which pypdf reads only with an added cryptography package. 376 fall below the usable bar. 13,131 more are left out before fetching: 9,293 have no link, Indiana's 2,782 need an API key, 918 link only amendments, 133 point at New Hampshire's retired host, 4 link an unsupported format and Tennessee's 1 is disallowed.

## Bill status

Every bill carries a status, `passed`, `passed_legislature`, `died` or `introduced`, derived from Open States' action classifications as of its archive's Generated At. The order of evidence is as follows.

1. **Enacted.** A chapter or act number, becoming law without a signature, or a veto override means `passed`, and is final whatever follows it in the record. A signature means `passed` too, unless a full veto falls on its day or later. Georgia's export classifies the governor's action date, "Date Signed by Governor", as a signature even on a bill the governor vetoed that day (SB 368 of 2023–24 carries both, and "Veto V12"), and Texas's classifies "Transmitted to the Governor" as one. A veto of items, a veto in part, and a conditional or amendatory veto (`lineage.status.PARTIAL_VETO_WORDING`, or Open States' `executive-veto-line-item`) leave a signed bill law: New Jersey's conditional veto is followed by a signature once the legislature adopts the governor's changes. Some exports record an enactment only in words, on an action with no classification: Oklahoma's "Becomes law without Governor's signature", Arkansas's "Approved by the Governor", Connecticut's "PUBLIC ACT 25-61", or a chapter number in Massachusetts, Florida, Oregon or Idaho. That wording counts as an enactment, with the reason `enacted-in-words`, but only on an action that carries no outcome classification, never for a motion to override a veto, and not when a full veto falls on its day or later, since Connecticut numbers a public act before the governor acts on it. `lineage stats` counts these per state and type (`reports/coverage.json`, `status_gaps.enacted_in_words`). *Corrected 2026-11-12.* Enactment had been final whatever followed it, on the belief that Georgia's veto after a signature was a line-item veto. Georgia's line-item veto reaches only appropriations, and SB 368 was vetoed outright. The correction changes 67 statuses, all from `passed` to `died`: 46 in Georgia, 11 in Texas and 10 in Connecticut, as `reports/coverage.json` (`status`) shows against its version before this change. None of them is a bill the commission's lists name, so recall is unchanged.
2. **Killed.** Otherwise, a veto, a failed vote or a failed override means `died`. The exception is a failed vote followed by a later passage, because chambers can reconsider. In that case the bill is alive again.
3. **Adopted.** Otherwise, a resolution that has been adopted is `passed`. Resolutions are adopted, not signed, so under the enactment rule alone an adopted resolution would show as died once its session ended. A simple resolution or memorial is adopted by its own chamber. A joint or concurrent resolution, a joint or concurrent memorial, and a measure classified as a constitutional amendment need both chambers. Passage actions name the chamber that acted, "Senate", "House" or "Assembly". A passage by a body named for the whole legislature counts for both chambers, because the exports use one only once every chamber has acted: Nebraska's unicameral legislature, Utah's enrolling step and Ohio's "Sent To The Governor". The deciding action is the adoption that completed the measure, so a page for a constitutional amendment names the vote that sent it to the ballot. An enrolled resolution was adopted, because enrollment follows adoption: Louisiana records the adoption itself only in words ("Read by title, rules suspended, adopted.") and classifies the enrollment.
4. **Legislature finished.** Otherwise, a bill the legislature finished with, and on which the record holds no outcome, is `passed_legislature`. The evidence is an action classified as enrollment or as the governor's receipt, or, where an export records that step only in words, the state's wording for it: Missouri's "Truly Agreed To and Finally Passed", Maine's "Passed to be Enacted", Ohio's "Concurred in House amendments", Massachusetts's "Enacted and laid before the Governor", and others in `lineage.status.FINISHED_WORDING`. Each phrase was chosen because it appears on nearly every enacted bill of its state and on almost no bill that died. Votes in both chambers are not enough. Read that way, Hawaii would have 1,019 such bills, nearly all conference deaths ("discharge of all conferees"), alongside Maryland's refused concurrences and New Jersey's bills replaced by their companions. The governor's action is missing from these records, still pending, or recorded somewhere the export does not reach, so the status claims neither enactment nor death. `lineage stats` counts them per state and type (`reports/coverage.json`, `status_gaps.passed_legislature`).
5. **Session ended.** Otherwise, a bill whose session ended before the archive was generated `died` with its session. A session is still sitting on its last day. Where bills carry over within a two-year term, the biennium's end applies ([Data snapshot](#data-snapshot)). A session with no known end date leaves the bill `introduced`, which avoids guessing that it died.
6. Anything else is `introduced`.

The table keeps the deciding classification (`status_reason`, or `enacted-in-words` or `session-ended`) and its date (`status_date`), so a bill page can name the action, for example a veto.

Explicit outcomes still come first. A joint resolution that goes to the governor and is vetoed `died`, and one that is signed names the signature. Joint and concurrent measures that only one chamber adopted die with their session; `lineage stats` counts them per state and type (`reports/coverage.json`, `status_gaps.resolutions_adopted_by_one_chamber`).

Actions are sequenced by date, and same-day actions keep the order the record lists them in. Louisiana, Nebraska, North Carolina, Wyoming, Colorado and Hawaii list a bill's actions newest first (96–100% of their multi-action records), and Kansas, Alabama and Montana vary by session. Read in Open States' `order` alone, a Louisiana veto came before the votes that preceded it, and the bill looked alive again. Dates arrive either as plain dates or as zoned timestamps. A timestamp is converted to a calendar date in the time zone the state's export uses. Most exports write a plain date as local midnight. Alabama's writes midnight Eastern although the state keeps Central time, and converting it with Central time would move each date a day earlier.

## Sections

The unit of matching is the section, not the bill. Provisions travel between states one section at a time, often inside omnibus bills, so whole-bill similarity would bury a shared provision under unrelated text. `lineage split` writes the `sections` table: bill id, ordinal, heading, display text, normalized text, and whether the bill was split at headings.

**Cleaning.** Before splitting, the text is cleaned:
- Line endings are unified.
- Style sheets left by the source's conversion from HTML are removed. Every Texas and West Virginia record with text carries style rules before the bill, and Texas's Word exports carry a whole style sheet inside an HTML comment. HTML comments are dropped. A style rule is dropped only when its line holds nothing but rules whose bodies are lowercase `property: value` declarations, because Kansas marks amendments with braces and other states brace parts of forms.
- Text is NFKC-normalized, so non-breaking spaces and ligatures become plain characters.
- Format, private-use and control characters are dropped. Kentucky's export, for example, puts a private-use glyph before each heading.
- Runs of spaces collapse to one.
- A printed line-number gutter is removed. A gutter is recognized only when most lines of the bill start with a bare number, so New Jersey's "1." section numbers and a line such as "2023 Regular Session" survive.
- Arizona's export markers are removed. Arizona's export wraps each code section in `START_STATUTE` and `END_STATUTE`, glued to the citation (`START_STATUTE6-251. Short title`), which would hide the citation from the heading rule and add a junk token to the shingles.
- Running page headers are removed. A header is a line that repeats at least three times in the bill, has at most eight words, contains a digit and has no lowercase letter, such as "LC 47 3375" or "STATE OF WYOMING 25LSO-0123". Repeated lines that read as text, such as "is amended to read as follows:", stay, and the document-frequency stoplist handles them.

**Headings.** A section starts at a line that opens with `Section 1.`, `SECTION 1.`, `Sec. 1.`, `SEC. 1.` or `§ 1.`, with a colon accepted in place of the period. The number can be code-style (`1-101`, `2a`, New York's `680-a`). Alaska's leading asterisk and Washington's `NEW SECTION.` are skipped. A heading must start its line, so a line opening with a quotation mark is not a heading. That keeps the sections of an act being amended, quoted inside the bill, from splitting it. Lowercase "section" at the start of a line is ignored, because there it is a wrapped cross-reference far more often than a heading. Text before the first heading becomes section 0.

**Citation headings.** A bill that enacts a new chapter often does so under one `SECTION 1.`, heading each code section with its citation alone (`19-35-1. Short title.`). Amending bills print the amended section the same way after the amending clause (`Section 4. Section 27-71-7, Mississippi Code of 1972, is amended as follows:` then `27-71-7. (1) ...`). Such a citation is a heading when it starts a line and is followed by a period, under these conditions:

- It has at least one hyphen, and every part after a hyphen starts with a digit (`6-3901.`, `9-33.2-10.`, `39-4A-2.`). That leaves out enumerators (`2.`), dotted outline numbers (`31.150.`), year ranges (`2025-2026.`) and New York's subdivision labels (`2-b.`). New York's sections themselves start with `§`.
- The line before does not end on a word that introduces a citation (`section`, `§`, `of`, `by`, `under`, `and`, `law`, `RSA`, `Pub. L.` and a few more), on a hyphen that breaks the citation itself, or on a struck citation in brackets that Utah replaces with the new one. One blank line between them changes nothing, and neither does a line number that a PDF left after a lowercase `section` ("under section 3"). Only that word takes a trailing number, since a page footer ("Page 2 of 3") or a title line ("ARTICLE 3") also ends in one and is followed by a real heading. In those cases the citation is a wrapped cross-reference.
- The bill already splits at section headings. A bill with none keeps the window fallback, because there a citation starting a line was a wrapped reference ("Public Law\n116-260."), and taking it turned one Ohio budget bill's windows into two sections.

**State heading rules.** Four states number bill or code sections in forms the general rules cannot take without misreading other states' lines, so each form is a rule for that state's bills alone, written from the state's own numbering:

- **North Dakota.** Century Code sections are title-chapter-section, and the legislature's PDFs space the hyphens (`59 - 22 - 01.`). These are citation headings.
- **North Carolina.** Bill sections are lettered into subsections (`SECTION 45.(a)`), and each General Statutes section a bill enacts or rewrites is printed in quotation marks (`"§ 50A-411.`). The lettered sections are section headings and the quoted statutes citation headings. Elsewhere a quoted line is never a heading, but North Carolina quotes every statute it enacts, so without the rule a new article is one section.
- **New Hampshire.** Bill sections are a number and a caption ending in a period (`1 New Chapter; Uniform Special Deposits Act.`, or `228:1` once the bill is chaptered), and RSA sections are chapter:section (`384-H:1 Short Title.`). New Hampshire numbers paragraphs in roman numerals, so a line opening with an arabic number and a caption is a bill section. A caption needs three characters before its period, which leaves out a wrapped `15 U.S.C.`
- **Missouri.** Bill sections are lettered (`Section A.`), and RSMo sections are chapter.section (`474.540.`). Every page after the first opens with the bill's number and the page (`SB 289 2`, `HCS HB 754 3`), which cleaning removes.

Each rule was measured over all of its state's bills, not only the bills the commission eval missed, and a seeded sample of the headings it adds was checked by eye. No bill loses a heading it had. Bills split at headings (`uv run lineage stats` → `reports/coverage.json`, `split_at_headings`, against the previous commit's file) go from 7 to 2,337 of New Hampshire's 2,515 and from 402 to 4,910 of Missouri's 10,722, and North Carolina's sections from 22,879 to 62,638. In North Dakota the rule reaches only the bills whose PDFs space the hyphens. On the commission eval, the four enactments lost to section size are found, in North Dakota (two), North Carolina and New Hampshire. One was lost: Missouri enacts the whole anti-SLAPP act as one RSMo section, so its bill was no longer cut into fallback windows, one of which had happened to align with an act section. Windows cut inside long sections find it again ([Windows](#windows)).

**Fallback.** A bill with no heading is cut into windows of at least 200 words on paragraph boundaries. A paragraph longer than a window is cut by words, and a short remainder joins the window before it. Every bill with text therefore yields sections, and the `by_heading` flag records which rule produced them. The exception is text that cleaning reduces to nothing, or to Texas's notice that a version's text is not available, which is treated as no text and counted as text without sections. `lineage stats` reports the heading hit rate per state.

**Normalized text** is case-folded words and numbers separated by single spaces, with the section sign spelled out so that "§ 2" and "Section 2" normalize alike. Shingling and hashing read it. The display text is kept for alignment and the site.

## Boilerplate

Enacting clauses, effective dates, severability clauses, repealers and amending formulas are near-identical across thousands of bills. Left in, they would make unrelated bills look alike. Two mechanisms remove them, and `lineage boilerplate` reports what each one caught in `reports/boilerplate.json` (committed). A third, the state boilerplate flag, finds a state's own clauses from the near-duplicate stage's pairs, and is measured for precision before it is adopted.

**Patterns.** A short list of patterns runs on normalized text and recognizes enacting clauses, effective dates, severability clauses and repealers, along with two of the Uniform Law Commission's standard closing sections: the uniformity clause ("In applying and construing this [act], ..."), which closes every uniform act, and the statement of an act's relation to the federal E-SIGN Act, which closes its acts on electronic records. Left in, those two made each uniform act's text match the enactments of dozens of other uniform acts (see [Commission recall](#commission-recall)). A section is flagged as boilerplate only when, once its heading and every pattern match are removed, at most four words remain, which is room for a catchline such as "effective date". A provision that ends with an effective date therefore stays matchable. So does a preamble that carries the bill's title along with its enacting clause. The `boilerplate` column records which kind a flagged section is.

**Document-frequency stoplist.** The patterns can't anticipate standard definitions, amending formulas ("is amended to read as follows"), or markup that survives extraction, such as Minnesota's "new text begin". The stoplist catches them from the data. Every matchable section's set of word 5-gram shingles is counted, and a shingle found in more than a set share of those sections is dropped before MinHash. Matchable means the bill's document type is eligible ([DR-5](#dr-5)) and the section is not flagged by the patterns, so the list reflects the text that will actually be compared: excluded resolutions cannot push their formulas onto it, and sections that are dropped anyway don't count twice. The list adapts to each state's habits without upkeep and is rebuilt with the corpus. The proposed share is 0.1% (`--max-share`). The report tabulates how many shingles, and what share of all shingle occurrences, each of several thresholds would remove, and lists the most frequent stoplisted shingles. The share was set before recall was measured and is not swept on the development set, since a value chosen there would be tuned to its 36 enactments. The held-out run checks it.

**State boilerplate.** A state's own standard clause, such as Texas's transition clause for criminal offenses or its request for a federal waiver, can stay under both the bucket cap and the stoplist, because one state's bills are a small share of the corpus. It then matches that state's bills from any other state's copy. Its sign is that the same text recurs across many unrelated bills of its state. `uv run lineage state-boilerplate` counts, for each signed section, the families of its own state, other than its own, that hold a verified near-duplicate of it (`same_state_pairs/`). Counting families rather than bills keeps a bill's versions and companions from counting more than once, and several competing bills on one topic count as a few families. A section that reaches 50 families or more is flagged. The flag belongs to the section, so it drops the clause from both stages: none of its cross-state pairs counts as a match, by wording or by meaning.

The counts have no valley to set the threshold by (`reports/state_boilerplate.json`, `histogram`). Of 2,873,256 signed sections, 1,421,447 reach another family. Half of those reach at most 2, and the counts thin out steadily to 13,530 sections at 1,000 or more. The threshold was set from what lies along that range, before any precision label was counted. Sampled sections at 200 families or more are clauses such as Texas's transition and waiver clauses and severability clauses. Interstate compacts sit lower. They are model legislation, which this project exists to trace, but different compacts are drafted from one template, so a compact's sections reach many of its state's other compact bills. Of the 6,542 signed sections that name a licensure or interstate compact, 90% reach at most 15 families and 99% at most 97 (`compact_sections`). A low threshold would drop much of the compacts' matching: at 10 families the flag would drop 1,438,842 of the near-duplicate stage's 2,441,208 cross-state pairs, and at 20, 227,755 (`sweep`). At 50 it flags 96,339 sections in 45 states, 98 of the compact sections among them, and drops 37,130 of the near-duplicate stage's cross-state pairs and 161,779 of the semantic stage's. Recall cannot show what the flag is worth, so precision is measured with it on and off, and the pairs it drops are sampled apart ([Precision sample](#precision-sample)).

**Shipped, 2026-11-11, except for pairs both stages found; the exemption widened 2026-11-12.** Of the pairs the flag drops, model-judged, 33% [23%, 47%] state the same provision beyond boilerplate, but 30 of the 34 found by both stages do, against 8 and 10 of the 34 found by one stage ([Known failure modes](#known-failure-modes)). So the flag does not drop a pair both stages found. The semantic stage's side of that is counted at 0.8905, the cosine that corroborates a match, not at the 0.94 a match by meaning needs to be listed on its own ([Choosing the threshold](#choosing-the-threshold)). As first shipped, at 0.93, the exemption counted the semantic stage at the threshold. The M5 review widened it on the flag's own dropped-pairs labels, not on any page sample: at 0.94, of the sampled pairs the widening alone keeps, found by meaning between 0.8905 and 0.94, 17 of 19 are correct, 0.89 [0.69, 0.97] (`uv run lineage eval precision` → `reports/results.json`, `precision.at_stage_threshold.exempted_by_corroboration`). At 0.94 the exemption keeps 13,182 near-duplicate pairs, every pair found by both stages that the flag would drop, 8,027 of them also listed by meaning; 30 of the 34 sampled are correct (`exempted_pairs`). The pairs the flag still drops are 0.12 [0.09, 0.45] correct (`dropped_pairs`). Both paths that list relatives apply it, a corpus bill's page and a query of new text, so they still list alike (`lineage.listing`); a query searches by meaning down to 0.8905 so that its exemption sees the same pairs. On the first tuning sample's Georgia pages at 0.94 the flag takes 33 of 355 listed relatives off and the widened exemption keeps 1 of them, and none of the sampled relatives changes: 14 of the 15 kept are correct with the flag off, on, on with either exemption, or on without one (`uv run lineage eval threshold` → `reports/threshold_proposal.json`, `state_boilerplate_flag`).

**Shingle hashing.** Each word is hashed with 64-bit FNV-1a over its UTF-8 bytes. Five consecutive word hashes are combined positionally and finished with MurmurHash3's 64-bit mixer, and the top 32 bits are kept. The computation is whole-array NumPy, and a test checks it against a one-shingle-at-a-time reference and pins its values. The stoplist and every later signature depend on those values, so changing the hash means rebuilding both.

## Windows

The section is the unit that is scored, grouped into families and shown, but a long section is not the unit that is compared. Jaccard similarity penalizes a difference in size. A 200-word act section wholly contained in a 2,000-word state section shares at most a tenth of their union, and with verification at 0.5 neither banding nor verification ever sees the pair: the S-curve proposes a pair at 0.1 with probability 0.003. What matching wants is containment, the share of the shorter text found in the longer, and windows of comparable size recover it with standard MinHash, leaving the estimator, the band index and the threshold as they are. Missouri showed the cost of comparing whole sections. It enacts the whole anti-SLAPP act as one RSMo section of about 2,000 words, and once its bills split at their own headings, that section's best similarity to any act section was 0.05 to 0.11 and the enactment was missed.

**The scheme** (`lineage.windows`). A section of at most 94 words is one window, itself. A longer section is cut into windows of 94 words, each starting 47 words after the one before, and the last window ends where the section ends. Neighbors share half their words, so where a provision sits in a section does not decide whether one window holds it: a test places provisions of 52, 94, 150 and 400 words at 52 offsets in a section of about 2,000 words, and at every offset some pair of windows has a Jaccard similarity of at least 0.5, while the whole sections' is under 0.25. Every shingle of a section lies wholly in some window, so cutting loses no shared text. Words are the display text's whitespace-separated words, which the semantic stage will embed, and each window is normalized as its section is.

**No unit larger than a window.** The first version kept a section of up to twice the window, 188 words, whole. Two copies of one section on either side of that limit, one kept whole and one cut, then compared a whole section with a window half its size, which holds their similarity near 0.49 however alike they are, so pairs that whole sections had matched were lost. With the limit at one window that gap is gone. A pair that whole sections match and windows miss is now one near the threshold whose edits are spread through the section, so that no pair of windows scores better than the whole.

**The size.** A window should be the size of the sections it is compared with. The median matchable section split at headings has 97 words, and the median of all matchable sections, the fallback's paragraph windows included, 138 (`uv run lineage index` → `reports/index.json`, `section_words`). That points to a window of about 95 words, and 94 keeps the stride at exactly half. A 94-word window runs to a median of 121 tokens and a 99th percentile of 200, within the shorter embedding model's 256 (`reports/semantic_sizing.json`, `tokens`). The semantic stage embeds windows of the same size ([Semantic stage](#semantic-stage)), so a pair the near-duplicate stage finds and a pair the semantic stage finds name the same windows.

**Matching by window, scoring by section.** Every window is signed and banded, and candidates and verification are pairs of windows. A section pair is verified when any pair of its windows is, and keeps its best pair's agreement count. Pairs are stored by section, family shares count a bill's sections, not its windows, and a query's score is the share of its signed sections matched. Results show the section, with its own heading.

**Cost.** 1,699,073 of the 2,898,322 matchable sections are longer than 94 words and are cut, and the index holds 16,671,477 signed windows where it held 2,873,256 sections (`reports/index.json`, `windows`): 5.8 times the rows, with the signatures, the band index and the build's time and memory growing in step ([Scaling limits](#scaling-limits)).

**Limits.** On identical text, windows recover a copied provision of 52 words or more wherever it sits in a long section, and edits raise that floor. A shorter provision is a small part of any window that holds it: one of 40 words reaches a Jaccard similarity of 0.40 against the window around it. Short provisions are left to the semantic stage, which compares meaning rather than shingle sets.

## Near-duplicate stage

Comparing every pair of sections is out of reach, so this stage summarizes each section in a short signature from which the similarity of any two can be estimated, and proposes for comparison only pairs whose signatures suggest they are alike. `lineage index` builds the signatures and the band index that proposes the pairs ([DR-3](#dr-3)).

**Shingle sets.** Each window ([Windows](#windows)) is represented by its set of distinct word 5-gram hashes, less the stoplist; a section of up to 94 words is its own single window. A window shorter than five words has no shingle, and one whose every shingle is stoplisted has none left. Neither gets a signature. A section with no signed window is not signed, and `reports/index.json` counts why: too short, or every shingle stoplisted.

**MinHash.** Each section's signature holds 128 values. Value *k* is the minimum over the section's shingles of *h*<sub>*k*</sub>(*x*) = ((*a*<sub>*k*</sub>·*x* + *b*<sub>*k*</sub>) mod *p*) mod 2<sup>32</sup>, with *p* = 2<sup>61</sup> − 1. Two sections' values at position *k* agree when the shingle that minimizes *h*<sub>*k*</sub> over both sets lies in both. Under an ideal random permutation that happens with probability equal to the sets' Jaccard similarity *J*, so the share of agreeing positions estimates *J* with standard error √(*J*(1 − *J*)/128), at most 0.044. A linear hash family only approximates an ideal permutation. The test oracle described below checks that the approximation costs neither bias nor spread.

**Exact arithmetic.** The product *a*<sub>*k*</sub>·*x* reaches 2<sup>93</sup>. Computed in NumPy's 64-bit integers it would wrap around before the remainder is taken, and the result would no longer belong to the family. The implementation splits *a*<sub>*k*</sub> at bit 32 and reduces each partial product using 2<sup>61</sup> ≡ 1 (mod *p*), so every value is exact. A test compares it with Python's arbitrary-precision integers on edge and random inputs.

**Keeping 32 bits.** The final mod 2<sup>32</sup> halves the signature's size, but two different shingles can now share a value. For two sets of *n* shingles each, a false agreement at one position has probability about *n*/2<sup>33</sup>. Signed by window, the largest measured set has 958 shingles (`reports/index.json`), which puts the bias at about 10<sup>−7</sup>, against a standard error of up to 0.044.

**Fixed parameters.** The 128 pairs (*a*<sub>*k*</sub>, *b*<sub>*k*</sub>) are drawn with SplitMix64 from a fixed seed rather than from a NumPy generator, because NumPy does not promise that its generators' streams stay the same across versions, and every stored signature depends on these numbers. A test pins them, along with sample signature values.

**Computation.** Each permutation runs over every shingle of a batch in one vectorized pass, and a reduction takes each section's minimum. Batches are cut into runs of about 131,000 shingles, so the working arrays stay in cache and are reused across permutations instead of being reallocated. Sections files are signed in parallel, one worker process per file.

**Storage.** Each sections file's signatures form one dense `uint32` matrix, one row per window, stored as `.npy` so it memory-maps as it is. Next to it, a Parquet file holds each row's bill id, section ordinal and window number. A section's windows are adjacent rows, and sections are numbered in row order. A signature takes 512 bytes.

**Test oracle.** datasketch, a development-only dependency, signs the same pairs of sets as the NumPy implementation: 200 pairs at each of five Jaccard levels from 0.1 to 0.9, with the exact similarity known by construction. For both engines, the mean error is within four standard errors of zero, and the two engines' means agree within the same bound. Each engine's root-mean-square error is within 20% of the theoretical standard error, since an error that is too small would point to correlated permutations just as surely as one that is too large. The two use different hash families, so the test compares estimates, not values.

**LSH banding.** Each signature is cut into 32 bands of 4 values. Two sections become candidates when all four values of at least one band agree. A pair with Jaccard similarity *s* agrees on a given band with probability *s*<sup>4</sup>, so it becomes a candidate with probability 1 − (1 − *s*<sup>4</sup>)<sup>32</sup>. That S-curve is 0.05 at *s* = 0.2, 0.56 at 0.4, 0.87 at 0.5 and 0.99 at 0.6, and it rises most steeply near (1/32)<sup>1/4</sup> ≈ 0.42. The setting leans toward recall, because verification discards a false candidate cheaply while a pair that is never proposed is lost for good. 32 × 4 was set before recall was measured and is not swept on the development set. The S-curve test shows how bands and rows move the threshold for the same 128 values: 16 × 8 raises it to 0.71 and 64 × 2 lowers it to 0.125, while a pair at the threshold is proposed with a probability near 1 − 1/*e* at each setting (`tests/test_lsh.py`). The held-out run checks the setting.

**S-curve test.** The curve assumes each band's four values come from independent permutations, which a linear hash family only approximates. So the test bands real signatures rather than simulated agreements: 500 pairs of sets at each of five similarities from 0.2 to 0.6, with the exact Jaccard similarity known by construction. At every level, the share of pairs that become candidates is within four binomial standard errors of the curve.

**Band keys and buckets.** Each band's four values are hashed to one 64-bit key with SplitMix64's finalizer. Equal keys from unequal bands would only add a candidate that verification removes, and with 16 million windows a band expects about 10<sup>−5</sup> of them. Each band's keys are sorted together with the row behind each key, and runs of equal keys are the buckets, so the index is two dense matrices of 12 bytes per window per band rather than millions of dictionary entries. It is stored in `bands/` beside the signatures and memory-mapped by queries. Pairs from all the buckets of one size are formed together from one matrix, and a pair that shares several bands is kept once. Identical windows share all 32 bands, so most pairs formed band by band repeat; repeats are dropped whenever the pairs held pass 2<sup>28</sup>, which bounds memory by the distinct pairs rather than by 32 times them.

**Bucket cap.** A bucket larger than the cap yields no pairs, and `reports/index.json` counts the buckets, window memberships and pairs skipped. The large buckets are boilerplate that the stoplist misses because it is common only within one state, such as a state's own wording of effective-date, appropriation and transition clauses. A cap set too low would also cut real copying: interstate compacts put the same section into bills in dozens of states. So the report sweeps a range of caps and, for each, counts the buckets skipped, those spanning more than one state, and the cross-state candidates the cap removes for good, after checking every band a pair shares. The cap is 2,000, the smallest cap in the sweep that removes cross-state candidates from no more than one bucket. It is a performance guard, not a precision control: verification and the boilerplate rules decide what counts as a match. While sections were signed whole the rule gave 1,000. Signed by window, clauses carried by dozens of states, such as the commission clauses that interstate licensure compacts share (enforcement, immunity, default), fill buckets of more than 1,000 windows: a cap of 1,000 would skip seven buckets that span states, one of them in 49, and drop 1,504,215 cross-state candidates (`lsh.cap_sweep`). Every build reports the cross-state candidates its cap drops (`lsh.capped.cross_state_pairs_lost`), and when the recall eval loses an enactment to the cap, its miss reason says so. The numbers are under [Measured facts](#measured-facts).

**Verification.** Each candidate's similarity is re-estimated from all 128 values and kept as the count of agreeing positions, one byte per pair. Pairs estimated below 0.5, fewer than 64 agreements, are dropped. The threshold of 0.5 is proposed. At 0.5 the S-curve already proposes 87% of pairs, so what verification keeps is what the bands find reliably, while below the curve's midpoint whether a pair is proposed at all is largely chance. The candidates' estimates show no valley to set the threshold by: cross-state candidates spread from 0.1 to 1 (`reports/index.json`, `pairs.estimate_histogram`). Partial or reworded copying below the threshold is the semantic stage's to find. The threshold was set before recall was measured and is not swept on the development set; the held-out run checks it. Candidates and verification are pairs of windows. The verified pairs become section pairs, each once with its best window pair's agreement count, and the cross-state ones are stored in `pairs/` by section number. Same-state pairs are stored apart, in `same_state_pairs/`. They form families and the state boilerplate flag ([Boilerplate](#boilerplate)) and are never matches.

**Families.** A state files the same text many times: companion bills in each chamber, a bill refiled in a later session, or one template for many resolutions. Lineage counts the other states that carry a provision, so each state's copies are grouped into a family that counts once. Two bills of one state are linked when, in each direction, at least 80% of the bill's signed sections have a verified match among the other's, and families are the connected components of the links. Requiring a share, not any one match, keeps a clause both bills happen to share from linking them. Requiring it in both directions keeps an omnibus bill from absorbing each small bill it contains. The share of 0.8 is proposed and was set from the measured distribution (`reports/index.json`, `families.min_share_histogram`). Shares spike at the fractions of small bills, 1/3, 1/2, 2/3 and 3/4, where a short bill shares one or two clauses with another, and again at 1. Between 0.70 and 0.95 they are sparse, and 0.8 sits there, past the 3/4 spike. The report's sweep shows what a lower share costs: at 0.5 the largest family grows to 3,846 bills and at 2/3 to 805, chained through shared clauses, while from 0.75 up it stays at 318. The largest families are one template filed many times, such as New Mexico's placeholder bills, Massachusetts's study orders and its placeholders for drafts with House counsel, which is what a family should collapse. A family is named by its first bill id in sort order and stored in `families/`.

**Query.** `lineage query FILE` treats a bill's text exactly as the corpus was treated: it is cleaned, split and normalized, boilerplate-only sections are set aside, and the rest are cut into windows, shingled, stoplisted and signed. Each signature's band keys are found in the memory-mapped band index by binary search, and a bucket over the cap yields nothing, as in the build. Each candidate is verified against its stored signature at the build's threshold. The query's sections are cut into windows as the corpus's are, and a query section matches a bill when any of its windows matches any of the bill's. Matches are grouped by family and ranked by the share of the query's words that fall in the sections the family matches, scored from the query's side so a provision carried inside a larger bill still ranks high ([Bill scoring](#bill-scoring)). A query reads only the index pages its keys land on and needs no network or API key. Results are shown through each family's best-matching bill, with the family's size.

## Semantic stage

The near-duplicate stage finds a provision a state kept in the act's words. A state that rewords the act as it enacts it is lost there: four of the development set's five remaining misses are proposed at an estimated similarity of 0.38 or below, or never proposed ([Commission recall](#commission-recall)). The semantic stage embeds every window with a local sentence-embedding model and finds each window's nearest neighbors by meaning, as a second candidate generator rather than a reranker of the first.

**Models.** Two small English models are candidates, both producing 384-dimension vectors: BAAI's bge-small-en-v1.5 (MIT license, trained to 512 tokens) and sentence-transformers' all-MiniLM-L6-v2 (Apache-2.0, trained to 256 tokens). They run through fastembed on ONNX Runtime, on the CPU. Each is pinned to a commit of the ONNX export fastembed itself uses, and each file to its hash; `uv run lineage model fetch` downloads them through the project's own HTTP client into `data/models/`, and a file that does not match is refused (`lineage.models`). Embedding then runs offline. Which model the stage uses is chosen by its quality on a labeled pair dataset, with speed breaking a tie: bge-small-en-v1.5 ([Pair dataset](#pair-dataset)).

**Sizing** (`uv run python -m benchmarks.semantic_units` → `reports/semantic_sizing.json`). Before the corpus is embedded, three units were measured: the near-duplicate stage's windows (94 words, stride 47), the same windows without overlap (94 words, stride 94) and windows twice as long (188 words, stride 94). For each, the benchmark counts the corpus's units and how many distinct texts they hold, measures their length in each model's tokens and each model's embedding rate on the reference laptop (Apple M1 Max, 10 cores, 32 GiB), and measures development recall.

Recall is measured on the development set, never the held-out one. Each act's sections are embedded as queries against the enactments' bills hidden among 3,000 bills drawn with a fixed seed. The draw leaves out 342 bills related to an act: the near-duplicate stage's relatives of each act, with their families, and bills whose title names an act or the lawsuits the Public Expression Protection Act addresses, since one related bill left in would set the cutoff by itself. An enactment is found when one of its bills has a window closer to an act section's windows than all but a fixed share of the (act section, drawn bill) pairs, 10<sup>−3</sup> or 10<sup>−4</sup>. Fixing that share rather than a cosine compares units fairly, because a coarser unit shifts every cosine.

Found counts are at a share of 10<sup>−3</sup>; at 10<sup>−4</sup> every cell is 35. Every miss is Maine's, whose stored text is the bill as first printed ([Parked](#parked)). The four reworded enactments the near-duplicate stage misses, Missouri's, Ohio's, Pennsylvania's and Oregon's, are found by either model in every unit. That is among 3,000 bills, not the corpus: a share of 10<sup>−4</sup> across every bill would still pass dozens per act section, which is why the stage keeps only each window's nearest neighbors, and why its precision over the whole corpus is measured on a labeled sample.

What the measurements show:

- **Overlap buys nothing measurable here.** Dropping it keeps recall and cuts the units by 38%. Each non-overlapping window is also one of the near-duplicate stage's windows, since both schemes start at word 0 and end at the section's last word, so a pair either stage finds still names the same windows.
- **Longer windows cost more and gain nothing.** 188-word windows are 16% fewer than non-overlapping 94-word ones but take longer to embed, because a unit's cost grows with its tokens, and a quarter of them exceed MiniLM's 256 tokens, which truncates their ends.
- **Identical text is embedded once.** In every unit measured, 27% to 30% of windows repeat another window's text exactly, in companion bills, refiled bills and templates. A text's vector is computed once and shared.
- **Embedding takes 12 to 25 hours, not one night.** The sizing embedded windows in the order drawn, at 30.3 non-overlapping windows a second for bge-small and 73.2 for MiniLM (`units_per_second`). A batch pads every text to its longest, so embedding windows in order of token count, which leaves each vector as it was to within float error, and splitting the work across four processes of two threads each raises that to 80.6 and 172.2 (`uv run python -m benchmarks.embed_throughput` → `reports/embed_throughput.json`). The distinct non-overlapping windows then take 25.2 and 11.8 hours. One process is fastest at eight threads, not ten: the M1 Max has eight performance cores and two efficiency cores, and a thread on a slow core holds up the rest. Other programs ran on the laptop throughout, as each run's recorded load average shows, so these rates are lower bounds.

**Index.** Every window retrieves its 20 nearest neighbors during the build. The non-overlapping windows' float16 vectors take 7.94 GB, counting a vector for every window, and their keys 0.08 GB. An HNSW graph over float32 vectors would take 18.5 GB, over the 16 GiB memory bound [DR-3](#dr-3) sets; over float16 vectors, 10.6 GB; IVF-PQ with 48-byte codes, 0.58 GB (`bytes`). A single query reads the memory-mapped float16 vectors directly: scanning them for a query of 20 windows takes 3.7 s with the file in the page cache (`exact_search_seconds_per_query`). The release download is the vectors, keys and model, about 8.1 GB in four assets under GitHub's 2 GiB limit.

**Decided, 2026-11-09.** The unit is the 94-word window without overlap, with each distinct text embedded once. The development set cannot separate the units: each finds 35 or 36 of the 36 enactments, and every miss is Maine's, which no unit can find. The choice therefore rests on cost, and the stage ablation and the held-out evaluation are its real checks. The build's nearest-neighbor index is IVF-PQ, with each candidate re-scored against its float16 vectors, unless a comparison against HNSW over float16 vectors and exact search on a sample overturns it. Single queries use exact search over the memory-mapped vectors. The corpus is embedded in one resumable run of up to three nights, which the measured 11.8 to 25.2 hours fit within.

**The run.** The corpus was embedded in two runs, the first stopped after 3.1 hours while the index comparison ran: 7,195,431 texts in 24.1 hours together, at 82.8 a second, against the 80.6 the throughput benchmark measured (`uv run lineage embed` → `reports/embedding.json`). The count leaves out 131,072 texts, eight shards embedded before runs were logged. Each of the four worker processes peaked at 1.90 GB. The vectors as stored take 5.63 GB rather than 7.94 GB, because the run stores one vector for each of the 7,326,503 distinct texts, not one for every window (`vector_bytes`), so the release download shrinks by the same amount. The sizing counted 7,305,861 distinct texts among the same 10,341,843 windows (`reports/semantic_sizing.json`, `94/94`), because it keyed each window by its words with whitespace collapsed, while the run keys it by its text as cut, line breaks included. 20,642 windows that differ from another only in their spacing are therefore embedded separately. The model's tokenizer ignores the difference, so each gets its twin's vector: they cost 0.28% more embedding and storage, and a twin can take one of a window's 20 neighbor slots.

**Index comparison.** The build's index was compared on a seeded sample of 1,000,000 embedded vectors, drawn from the 63 of 448 shards embedded at the time, with 2,000 further vectors as queries and exact search as the truth (`uv run python -m benchmarks.ann` → `reports/ann_benchmark.json`). What matters is the share of each query's true neighbors at a cosine of 0.8905 or more that an index finds, since those are the only ones the stage keeps; the sample held 7,028.

| Index | True neighbors above the threshold found | Of the exact 20 nearest | Queries a second | Index bytes, projected to the corpus |
|---|---|---|---|---|
| HNSW32 over float16 vectors, efSearch 128 | 0.9989 | 0.9798 | 16,745 | 7.62 GB |
| HNSW32 over float16 vectors, efSearch 64 | 0.9976 | 0.9617 | 31,020 | 7.62 GB |
| IVF-PQ, 4,096 lists, 48-byte codes, 32 probed, 100 re-scored | 0.9721 | 0.8459 | 10,364 | 0.46 GB |
| IVF-PQ, the same, 64 probed | 0.9745 | 0.8687 | 8,042 | 0.46 GB |

IVF-PQ's recall stops rising as more lists are probed: its 48-byte codes rank some true neighbors outside the 100 candidates re-scored, so no amount of probing recovers them. HNSW over float16 vectors loses about a tenth as many and searches faster. IVF-PQ was preferred for memory, when an HNSW graph was estimated at 10.6 GB over float16 vectors; measured, it projects to 7.62 GB, within the 16 GiB bound. The projection scales the sample linearly, and a text has more neighbors in the whole corpus than in a sample of a seventh of it, so `lineage neighbors` searches 2,000 seeded texts exactly once the build is done and reports the build's recall over the whole corpus (`reports/neighbors.json`, `exact_check`).

**Index decided, 2026-11-09.** The comparison overturned IVF-PQ. The build's index is HNSW32 over float16 vectors at efSearch 128, the widest setting measured, since its search over the corpus is projected at minutes. Its scores are cosines over the float16 vectors already, so nothing is re-scored.

**The index is built, used and discarded.** `lineage neighbors` keeps what the index finds, each text's neighbors in `ids.npy` and `scores.npy`, and never saves the index itself, so the index release does not ship it. A single query needs no index: it searches the memory-mapped float16 vectors exactly ([Index](#semantic-stage)). The build holds its memory to the 16 GiB bound [DR-3](#dr-3) sets. Before it starts, it projects its peak from the index's measured bytes per vector and its working buffers, and refuses a projection over the bound. While it runs, it checks its footprint after training and after every batch of vectors it adds or searches, and stops at the first crossing. The check compares the lifetime maximum as well as the footprint at that moment, because a spike inside one faiss call is over before the call returns. Its report records the projection and the measured peak. It also stops when its exact check finds less than 0.99 of the true neighbors above the threshold, to be run again with a wider search (`--ef-search`).

**The build** (`uv run lineage neighbors` → `reports/neighbors.json`). Over the whole corpus each of the 2,000 checked texts has more true neighbors above the threshold than in the sample, 13,937 in all against the sample's 7,028, and efSearch 128 found less than the 0.99 floor of them. At efSearch 256 the build finds 0.9938 (`exact_check`). At the stage's threshold of 0.94, set later ([Precision sample](#precision-sample)), the same 2,000 texts have 6,652 true neighbors and the stored neighbors hold 0.9938 of them, so no rebuild was needed (`uv run lineage neighbors --check-at-stage` → `exact_check_at_stage_threshold`). It indexed the 7,326,503 texts in 350 s and took 4,456 s in all, including a pause while the laptop slept. It peaked at 7.88 GiB, against a projection of 9.25 GiB and the 16 GiB bound (`peak_memory_bytes`, `projected_memory_bytes`). The first full build peaked over the bound, though the index itself was within its projection: measuring the index's size for the report copied it into memory a second time, and the copy grew to twice the index. The size is now counted as faiss writes the index out, and nothing is copied. 6,249,724 texts, 85% of them, have at least one neighbor at a cosine of 0.8905 or more, and the build keeps 51,588,148 neighbors in all, at most 20 a text (`texts_with_a_neighbor`, `neighbors_kept`).

**Section pairs, decided 2026-11-10.** The build stores the semantic stage's matches as cross-state section pairs, the near-duplicate stage's unit, rather than leave every reader to expand the text-level neighbors. Two sections match by meaning when a window of each carries the same text, or two texts one keeps as a neighbor of the other. Each pair is stored once, numbered by section as the near-duplicate pairs are, with its best cosine and the window pair that gave it, so alignment and explanations can point to the text that matched and the cap of 20 stays traceable. The precision sample's strata, bill scoring and the export then read both stages alike. Same-state pairs are not stored, since families come from the near-duplicate stage. The table records the model, K and threshold it was built under, and refuses to load under another model or K, or at a threshold under its own, until it is rebuilt. It is built down to 0.8905, the pair dataset's threshold, and read at the stage's, 0.93: each text keeps its 20 nearest before a threshold applies, so the pairs at or above a stricter threshold are exactly those a build at it would store (`lineage.semantic_pairs`).

**The pairs** (`uv run lineage semantic-pairs` → `reports/semantic_pairs.json`). The 51,588,148 kept neighbors give 3,903,851 cross-state section pairs, against the near-duplicate stage's 2,441,208 ([Measured facts](#measured-facts)). 51,840 of them are at a cosine of 1, the same text in both (`pairs_at_cosine_1`), and the rest spread down to the threshold, 1,077,516 of them within 0.011 of it (`cosine_histogram`). The 25,066 sections the near-duplicate stage does not sign, too short for a shingle, have no section number and their windows are left out (`sections_left_out`). The build took 13 s and peaked at 3.76 GiB, its join held to 6 GB by DuckDB's memory limit (`seconds`, `peak_memory_bytes`). The pairs take 78 MB (`bytes`).

**efSearch raised, 2026-11-10.** The build searches at efSearch 256, not the 128 decided above, because 128 fell under the recall floor over the whole corpus. The index is unchanged.

## Commission recall

The external ground truth is the Uniform Law Commission's list of enactments. Starting from a uniform act's text, the eval asks what share of the bills that enacted it the pipeline finds.

**Development and held-out sets.** The enactments of the first three acts in the table below were used for diagnosis: the fixes made since M3 were chosen by studying their misses. Their recall is therefore a development number, not an estimate of recall on acts the project has not seen. A second answer key, of enactments of uniform acts not examined and of bills not in the first set, is committed before any further tuning. Its bills may be resolved, but the eval is not run against it and its matches are not inspected until the final evaluation at the end of M5. It is then reported once, as held-out recall, beside the development number.

The held-out acts are the Uniform Assignment for Benefit of Creditors, Easement Relocation, Mortgage Modification and Directed Trust Acts. They were chosen by the commission's count of enactments listed in 2023–2026, which says nothing about what the pipeline finds. The selection rule was fixed before the lists were read. It takes every enactment listed in 2023–2026, except the District of Columbia and any row that names a bill of the development set: a bill that enacted two acts has already been studied. If more than 22 remained, a seeded sample would keep at most six per act. If fewer than 18 remained, the reserve acts would be added in order, Health-Care Decisions and then Antitrust Pre-Merger Notification. `evals/ulc_enactments_heldout.csv` holds every row of the six acts' bill lists, the reserves included, read on 2026-11-07; a reserve act's rows are listed but not counted. `uv run lineage eval answer-key --held-out` resolves it to bills in `reports/answer_key_heldout.csv`, which runs no matching: 19 enactments are counted, and each resolves to a bill in its listed year. `uv run lineage eval commission --held-out` refuses to run without `--final`, and the final run writes its own section of `reports/results.json`. The act texts are read from `data/acts/held-out/`. Before the final run, the act-text parser may be checked and fixed against those texts alone: the sections it keeps are compared with each act's headings, never with bills or match output.

**Held-out recall, run on 2026-11-12, first at 0.93 and then at the final configuration.** The held-out acts were first run with the threshold at 0.93 and the state boilerplate flag as first shipped, and found 17 of their 19 enactments, 89.5%. The M5 review then moved the threshold to 0.94 and widened the flag's exemption, both decided on tuning data without reference to that run ([Choosing the threshold](#choosing-the-threshold)), and ruled that the held-out acts be run once more at the final configuration. At 0.94 with the widened exemption they find the same 17 of 19, 89.5%, against 33 of 36 on the development set (`uv run lineage eval commission --held-out --final` → `reports/results.json`, `commission_held_out`; the first run under `earlier_runs`). The near-duplicate stage alone finds 15 and the semantic stage alone 17, as at 0.93. The semantic stage adds Pennsylvania's Directed Trust enactment and Nevada's Mortgage Modification enactment, at best cosines of 0.9735 and 0.9623, so neither raise cost them. Both misses are never proposed by the near-duplicate stage. Iowa's Assignment for Benefit of Creditors enactment reaches a best cosine of 0.6804 with the act. Virginia's Easement Relocation bill, listed as substantially similar, reaches 0.8901, under 0.8905 as well as 0.94 (each bill's `best_cosine`). As with the development misses, neither changes matching. The command refuses to run the held-out acts again at a configuration they have been run at (`lineage.commission.check_held_out_configuration`).

**Act text.** The ULC holds the copyright in its acts. Its [terms of use](https://www.uniformlaws.org/termsofuse) let anyone view, copy, print and distribute the site's content for informational, noncommercial purposes, unmodified and with the copyright notice or other attribution. Modifying it is allowed only as part of a legislative process. The terms say nothing specific about showing an act on another website. Downloading an act's final text shows no separate notice or terms. Each act prints its own notice in its front matter:

| Uniform Public Expression Protection Act | Final act without prefatory note and comments, October 2, 2020 | Copyright © 2020 By National Conference of Commissioners on Uniform State Laws |

So:

- The repository never contains act text. Its code is MIT-licensed, and an act committed beside it would read as offered under that license, which includes the right to modify. Act texts live in `data/acts/`, which is gitignored, and each user downloads them from the ULC under its terms (README, [Data](README.md#data)).
- The eval uses them locally, as query documents.
- The site may show an act's text unmodified, with the act's own copyright notice above and a link to the act's page, as informational, noncommercial use. No narrower notice came with the download, so the terms of use are the whole of the permission.

**Act texts as queries.** An act as the commission publishes it is mostly not law: a title page and committee list, a table of contents, a prefatory note, and an official comment or legislative note after many sections. States enact the sections. Scoring is from the query's side, the share of the query's sections a bill matches, so every comment left in would lower every enacted bill's score. The editions above already leave out the prefatory note and comments, but each still carries legislative notes, which tell a state how to adapt a section and can run several paragraphs. `lineage.acts` keeps the numbered sections, including bracketed optional ones, and the article headings of an act divided into articles. It drops the front matter up to the first section or article heading that is not a contents entry, and each comment or legislative note up to the next section or article heading. In the commission's final acts, both close a section. The words each act keeps, and each file's SHA-256, are recorded in the eval's results, so a different edition or conversion is visible.

**Placeholders.** The commission marks in brackets the text a state adapts: placeholders such as "[this state]" or "[insert citation]", alternatives such as "[shall][may]", and optional clauses and sections. The query keeps them as written, and an optional section stays a section. A placeholder a state keeps generic, "[act]" enacted as "act", normalizes like its word and costs nothing. One a state fills in changes the shingles around it. Where a section has only a few, the near-duplicate stage still proposes and verifies it. Where they are as dense as in the development acts' densest sections and a state fills in every one, the section is still proposed but falls under the verification threshold, so it is the semantic stage's to find. Tests pin both cases on an invented section (`tests/test_acts.py`), and matching does not treat brackets specially ([Parked](#parked)).

**Finding an enactment's bills.** The ground truth is `evals/ulc_enactments.csv`, every row of each act's bill list on the day it was read. Rows the list shows only as introduced are not enactments and are skipped. The District of Columbia is excluded, since the corpus is the 50 states, and so are enactments listed before 2023, where the corpus begins. Enacted and Substantially Similar are reported as separate strata. A row's cell can name several bills, usually companions in each chamber, so bill numbers are compared in one form: Colorado's year prefix ("HB 24-1232") is dropped, and "H 40" and "HB 40" compare equal. Each enactment's bills are found by state, number and session year, in three steps:

1. Every bill the cell names in a session whose years contain the listed year. A bill shown passed after that year is a later bill reusing the number and is dropped. If any of the rest passed, these are the enactment's bills.
2. Otherwise, a named bill that passed in the session ending the year before. The list's year can be the signing year: Ohio's act passed both chambers in December 2024, the last month of its session, and is listed under 2025.
3. Otherwise, the bills of step 1, recorded as matched by number only.

"Passed" is a passed status, or a passage action recorded in every chamber, since a bill signed after its session ends can still carry a status of died. `lineage.ulc` implements the rule, and each enactment's results name the step that matched it.

The resolved mapping is committed as `reports/answer_key.csv` (`uv run lineage eval answer-key`) so every row can be checked by eye. Each bill a row resolved to is listed with its Open States id, title, chambers passed and last passage date, along with the step that found it and the listed number it matched. Rows that are not counted are listed with the reason. The key needs only the bills table, so it can be checked before the index is built. A test fails if the committed key and the committed results name different bills.

**Found.** An enactment is found when any of its bills belongs to a family among the act text's relatives with a score above the threshold. The score is the share of the act's words in the sections the family matches, the share that query-side scoring ranks by ([Bill scoring](#bill-scoring)). Rank is reported but does not decide. A uniform act's real relatives can outnumber any fixed rank once each state's introduced, failed and enacted versions count, so a rank cutoff would cap recall as an act spreads. The site's display cap of 50 relatives is a separate choice.

The threshold comes from the measured scores, and recall at higher thresholds is reported beside it. An earlier rank cutoff of 50 was examined first. With the commission's standard closing sections still matchable, most of each act's relatives were bills of other uniform acts matched through the uniformity clause alone, or through the E-SIGN statement, and they outranked some enactments. Those two sections are now boilerplate ([Boilerplate](#boilerplate)). Every relative left for each of the three acts carries part of that act's text. Each is an enactment, another state's introduced or failed bill, a companion, an omnibus bill that includes the act, or a bill that adapts a few of its sections. The results list them (`queries.<act>.relatives`). No score separates unrelated bills from relatives, so the threshold is one verified section (`threshold.min_share` 0). The results record each found enactment's rank and share, and recall at higher minimum shares (`recall_by_min_share`), so another threshold can be read from them without rerunning. The threshold is re-examined whenever a relative turns out not to carry the act. An enactment is "with text" when at least one of its bills has stored text, and recall is reported over all enactments and over those with text.

**Miss reasons.** Each miss is classified automatically. Each bill an enactment names gets the first reason that applies, and the enactment takes the reason of the bill that got furthest through the pipeline. The stage reasons are measured by replaying LSH and verification on the bill's own stored signatures, with the query's band keys, the bucket cap and the verification threshold. With both stages, only an enactment neither stage finds gets a reason, and the reason says where the near-duplicate stage lost it. The semantic stage's side is each bill's best cosine to the act, whether or not the stage kept it.

- `not_in_corpus`: no bill the cell names is in the snapshot in the session years.
- `no_text_in_source`: the bill has no text in the corpus, exported or fetched.
- `amendment_only`: the stored text is an amendment that does not replace the whole bill (see [Known failure modes](#known-failure-modes)).
- `excluded_type`: the document-type rules exclude the record ([DR-5](#dr-5--match-only-document-types-that-can-carry-law)).
- `no_usable_text`: the text yields no signed section, because every section is boilerplate or stoplisted.
- `not_proposed`: no window of the bill shares a band key with any window of the act.
- `bucket_cap`: a window pair would have verified, but every band it shares is in a bucket over the cap.
- `verification`: a window pair was proposed, but none reached the verification threshold.
- `below_threshold`: the bill's family is among the relatives, with a score at or below the threshold.

**Pipeline regression test.** The act texts cannot be committed, so CI cannot compute the headline number. Instead, `tests/test_commission.py` runs every pipeline command on a committed fixture: the bills each enactment names, among distractors that are bills of other uniform acts from the same archives. They share the commission's drafting conventions and closing sections, which makes them hard negatives. Each act is queried with its earliest enacted state version, and that version's own enactment is left out. The test fails if any enactment it found when written is lost. `uv run python -m evals.fixture` rebuilds the fixture from the snapshot. It leaves out omnibus bills over 40,000 characters. Its number is not the recall the README reports, because a state's version differs from the act.

**Results.** `uv run lineage eval commission` writes the `commission` section of `reports/results.json`: recall pooled, per act and per stratum, the same for each stage alone ([Stage ablation](#stage-ablation)), the miss-reason counts, and each enactment with its bills, their stages and their best similarity to the act. It also records the SHA-256 of the enactment file and of each act's text, before and after the comments and notes are dropped. The README's results table is generated from this file.

**Development misses and the stage that owns them.** With the fetched text, the near-duplicate stage misses 5 of the 36 development enactments (`reports/results.json`, `stage_ablation`, and each enactment's `found_by_stage`). Missouri's, Ohio's and Pennsylvania's are proposed but lost at verification, their best window pairs estimated at 0.38, 0.33 and 0.35 against the act. Oregon's, listed as substantially similar, is never proposed, at 0.16 (each bill's `best_estimate`). Their bills put the act in other words, which is the semantic stage's to find, and it recovers two of them ([Stage ablation](#stage-ablation)). Maine's is never proposed because its stored text is the bill as first printed, while the enacted wording is in a separate document of adopted amendments ([Parked](#parked)). None of the five is a reason to tune the near-duplicate stage further.

## Pair dataset

The commission's lists test whether the pipeline finds enacted uniform acts. They cannot set the semantic stage's similarity threshold without tuning it on the 36 development enactments, and they say nothing about sections that are related without being copies. A labeled pair dataset does both.

**The dataset.** Kim, Griggs, Kim and Oh, "Learning Bill Similarity with Annotated and Augmented Corpora of Bills", EMNLP 2021 ([aclanthology.org/2021.emnlp-main.787](https://aclanthology.org/2021.emnlp-main.787)). Annotators labeled 4,721 pairs of subsections of US congressional bills on a five-point scale from unrelated (0) to identical (4), split into 3,305 training, 472 validation and 944 test pairs. The texts are cut at 400 words and stripped of punctuation. A pair counts here as positive when it is labeled related (2) or closer. The bills are congressional, not state, so the dataset measures how each stage scores relatedness, not how the corpus's own text behaves.

**Terms.** The authors' repository publishes no license. The files are therefore used locally for evaluation only. `uv run lineage pair-data fetch` downloads them at a pinned commit, each checked against its git blob id, into the gitignored `data/pair_data/`. They are never committed, redistributed or downloaded in CI; only the metrics computed from them are committed. Asking the authors for a license is parked ([Parked](#parked)).

**The near-duplicate stage** (`uv run lineage eval pair-data` → `reports/pair_data.json`). Each subsection is treated as a section: cut into windows, shingled, stoplisted with the corpus's stoplist and signed. A pair is found when two of its windows share a band key and verify at an estimate of 0.5, as in the build. On the test split the stage finds 77.3% of the positive pairs at a precision of 97.8%. By label, it finds all 160 identical pairs, 80 of 105 almost identical, 70 of 136 related, 6 of 60 partially related and 1 of 483 unrelated. Its best window agreement alone ranks a positive pair above a negative one with a probability of 0.987 (ROC AUC). What it misses is related pairs that share meaning more than wording, which are the semantic stage's to find.

**The semantic stage** (same command and report). Each subsection is cut into 94-word windows without overlap, as the stage cuts sections, and a pair scores its best cosine between windows. Each model's threshold is set on the 3,777 training and validation pairs as the lowest cosine whose precision there reaches 0.9, and only then applied to the test pairs.

| Model | ROC AUC, development / test | Threshold at 0.9 | Test precision / recall at 0.9 | Test precision / recall at 0.95 |
|---|---|---|---|---|
| bge-small-en-v1.5 | 0.987 / 0.986 | 0.8905 | 0.889 / 0.955 | 0.943 / 0.913 |
| all-MiniLM-L6-v2 | 0.982 / 0.980 | 0.840 | 0.878 / 0.933 | 0.929 / 0.883 |

bge-small is ahead at every precision measured and in ROC AUC on both sets of pairs, so it is the stage's model, and speed, the tie-breaker, does not come into it. It takes 25.2 hours to embed the corpus against MiniLM's 11.8 ([Semantic stage](#semantic-stage)), within the three nights the run is allowed. At its threshold it finds 122 of the 136 related pairs, of which the near-duplicate stage finds 70, and every pair the near-duplicate stage finds. It also passes 13 of the 483 unrelated pairs and 35 of the 60 partially related ones (`semantic.models`, `by_label`).

**What the threshold means for the corpus.** It is set before development recall is measured, so the 36 enactments do not tune it (`lineage.semantic`). Its precision is the dataset's: 42% of the test pairs are positive, while almost none of a corpus window's neighbors are. In the corpus, then, the threshold is a floor under each window's 20 nearest neighbors, not a test that makes them precise, and the precision sample measures what it passes. It could change only on the precision sample's evidence, never on development recall, and on that evidence pages now list matches by meaning at 0.93 ([Choosing the threshold](#precision-sample)). The build still keeps every match down to 0.8905, so the options between the two stay measurable without rebuilding. The dataset's texts are also stripped of punctuation, which the corpus's windows keep.

`uv run lineage eval commission` queries each act through both stages and records, for each enactment, which stages found it (`reports/results.json`, each enactment's `found_by_stage`). The ablation counts recall for each stage alone and for both together, pooled, by act and by stratum (`stage_ablation`). `--no-semantic` runs the near-duplicate stage alone.

| Stage | Electronic Estate Planning Documents | Public Expression Protection | Special Deposits | Pooled |
|---|---|---|---|---|
| Near-duplicate alone | 8 / 9 | 10 / 14 | 13 / 13 | 31 / 36 |
| Semantic alone | 9 / 9 | 11 / 14 | 13 / 13 | 33 / 36 |

**What the semantic stage recovers.** It finds all 31 enactments the near-duplicate stage finds, and two of the four reworded ones that stage misses ([Commission recall](#commission-recall)): Missouri's and Ohio's. Both rank low, Missouri's at 19 and Ohio's at 38, because each matches only one or two of the act's sections (`rank`, `share`). They carry part of the act, reworded, not the whole of it.

**What both stages miss.** Pennsylvania's enactment names two bills. SB 972's best window reaches a cosine of 0.8951 with the act, and HB 1466 0.8904, both under the stage's threshold of 0.94. At the pair dataset's 0.8905, SB 972 was above the threshold but not among the 20 nearest corpus texts of the act window it matches, so the stage never kept it. Oregon's, listed as substantially similar, reaches 0.8830, and Maine's 0.8167, for the reason given in [Parked](#parked) (each bill's `best_cosine`). Development misses do not tune matching, so neither the cap of 20 nor the threshold changes for Pennsylvania. A wider cap is parked.

**What the semantic stage adds to a query.** At the stage's threshold of 0.94, with the state boilerplate flag ([Boilerplate](#boilerplate)), an act matches 16 families by meaning against 12 by wording for Electronic Estate Planning Documents, 35 against 39 for Public Expression Protection, and 17 against 25 for Special Deposits (`queries`, `families_by_stage`). 7 families across the three acts are found by meaning alone. Each matches a single section of the act, and 3 of them hold a development enactment (each relative's `sections_by_stage` and `enactment`).

**Recall only.** The commission's lists name the bills that enacted an act, not the bills that did not, so they cannot show that a match is false. On these 36 enactments, recall gives no reason to keep the near-duplicate stage, since the semantic stage alone finds everything both stages find. The near-duplicate stage's case rests on its exact spans for highlighting, its lower cost, and its precision on boilerplate that sounds alike. Each stage's precision is measured on the labeled precision sample (M5). Both stages stay, and what the sample measures the near-duplicate stage adding beyond recall is reported under [Alternatives considered](#alternatives-considered).

## Bill scoring

**The score.** A family's score is the share of the query bill's words that fall in the sections it matches, of the words of every section either stage searched: the signed sections, and with the semantic stage every matchable section with a word. Scoring from the query's side keeps a provision carried inside a large omnibus high, where scoring against the omnibus's own length would bury it. Weighing sections by their words, rather than counting them, keeps a short section, such as a title or an effective date, from counting as much as the provision itself. A state's copies of a bill are one family and count once (`lineage.query.group_matches`).

**A corpus bill's relatives.** A bill already in the corpus needs no search. Its matches are both stages' stored cross-state section pairs ([Semantic stage](#semantic-stage)), read as a page lists them: by meaning at the stage's threshold, and without the state boilerplate flag's pairs ([Boilerplate](#boilerplate)). A query of new text lists its own hits by the same rules, and both are scored by the same function, so a bill and a query of its text score alike; tests hold the two equal on the commission fixture, with the flag and without (`lineage.listing`, `tests/test_relatives.py`, `tests/test_listing.py`). Every related family in another state is counted, and the 50 best are kept for the bill's page (`lineage.relatives`). Any matched section is enough to be listed, as it is to be found. Whether an enactment counts as found never depends on the cap ([Commission recall](#commission-recall)).

**What scoring by words moves** (`uv run lineage eval commission` → `reports/results.json`). Development recall is unchanged, 33 of 36, since a family that matches one section of any length is still found. Ranks move. A family that matches one long section of an act by meaning, often its definitions, now outranks one that matches several short sections, so Electronic Estate Planning Documents' enactments in Minnesota and Missouri rank 13 and 15 (`rank`). Where enactments must share at least half the act's words, 27 of the 36 are found (`recall_by_min_share`).

## Alignment

A match says two sections are related; alignment shows where. Both display texts are read as words, each keyed by its normalized form, so case and punctuation do not break a copy, and `difflib` finds the blocks of words the two share in order (`lineage.align`).

- **Copied:** a shared block of at least five words, the shingle length. A shorter one ("the state shall") is common phrasing, not evidence, and is not kept.
- **Paraphrased:** a sentence paired by meaning. Between the copies, and over the whole pair when nothing was copied, each side's unmatched stretch is cut into sentences and clauses, and sentences are paired by the semantic stage's model: a pair whose cosine reaches 0.8905, the pair dataset's threshold, is a paraphrase. It stayed there when pages came to list matches by meaning at 0.93 and then 0.94 ([Precision sample](#precision-sample)): every Georgia sample was judged on passages aligned at it, and which bills a page lists is a separate question from which sentences of a listed pair read alike. Inside a relative already listed, 0.8905 only corroborates; it never lists a relative by itself ([Choosing the threshold](#choosing-the-threshold)). Pairs are taken best first and never cross, so each text still reads in order. Without the model, nothing is marked as paraphrase.
- **Unmatched:** every sentence left unpaired, on either side.

Every span has an id in reading order and its character offsets in both texts, so the site can highlight it and an explanation can cite it, which code checks ([Constraints](#constraints)). Junk detection is off, since it would treat frequent words such as "the" as unmatchable in long sections.

## Precision sample

Recall has an answer key; precision needs labels. A seeded sample of matches, drawn per stage, is labeled on the labeled pair dataset's scale: 0 unrelated, 1 partially related, 2 related, 3 almost identical, 4 identical.

**What counts as correct.** A match is correct when it is labeled 2, 3 or 4, and wrong when it is labeled 0 or 1. That is the bar the semantic stage's threshold was set to on the pair dataset ([Pair dataset](#pair-dataset)), so precision in the corpus and on the dataset measure the same thing. This is fixed before any label is counted.

**The sample.** The build's cross-state section pairs fall into three strata by the stages that found them: the near-duplicate stage alone, the semantic stage alone, or both. Each stratum is sampled apart, without replacement under a fixed seed, so a stage that finds few pairs is still measured and the draw repeats exactly over the same build. The size is 100 pairs per stratum for now; the final size is decided after release, once the provisional labels show how wide the intervals are. The drawn pairs are shuffled into one labeling order, so a session stopped part way has covered every stratum about evenly. The sample file names each section by bill id and ordinal and holds no text. `uv run lineage precision-sample` draws it from both stages' stored cross-state pairs ([Semantic stage](#semantic-stage)) into `evals/precision_sample.jsonl`, and records the seed and each stratum's size in `reports/precision_sample.json`. Of the build's pairs, 1,392,446 are found by the near-duplicate stage alone, 2,855,089 by the semantic stage alone and 1,048,762 by both (`strata`), so the weighted estimate leans on the semantic stratum. The pairs the state boilerplate flag drops ([Boilerplate](#boilerplate)) are sampled apart, 34 per stratum under the next seed, so their precision is measured directly rather than from the few of them the main sample holds (`uv run lineage precision-sample --flagged` → `evals/precision_sample_flagged.jsonl`). The flag drops 23,948 pairs found by the near-duplicate stage alone, 148,597 found by the semantic stage alone and 13,182 found by both (`reports/precision_sample_flagged.json`, `strata`).

**The scale.** Each label comes with a definition, the same for a person and for a model: 0 unrelated, different subjects; 1 partially related, a shared subject but different provisions; 2 related, the same provision or purpose, worded or detailed differently; 3 almost identical, the same provision in mostly the same words, with small edits; 4 identical, the same text apart from formatting, numbering or place names. The names are the pair dataset's; the definitions are this project's.

**Labeling.** `uv run lineage label SAMPLE --labeler HANDLE` shows each pair's two sections aligned ([Alignment](#alignment)) and asks for a label. The labeler is not told which stages found the pair, and pair ids are numbered in labeling order, so neither can sway a label. Each label is appended to `evals/precision_labels.jsonl` as soon as it is given, so labeling stops and resumes at will.

**What a label records.** Each side's Open States bill id and the SHA-256 of its section's normalized text, which survive a re-split of the corpus. The section's heading and ordinal are kept for reading only, since a re-split renumbers sections. When labels are loaded, any whose text no longer matches a section of its bill is dropped and counted. The file holds no bill text.

**Who labeled.** A person is recorded by GitHub handle, and the tool refuses anything that is not one. A provisional label from a model is recorded by model id and prompt version. Only a person's label takes a pair off the list.

**Provisional labels.** `uv run lineage label-model SAMPLE --live` asks a model for each pair's label, from the two section texts and the scale alone, through the Anthropic SDK with structured output: one label, no prose. Each is appended to the same file under the id of the model that served it and the prompt version, and the file is the cache, so a pair is asked once per prompt version. Without `--live` the command says how many pairs it would ask, and what they are projected to cost at most, and asks none. The projection counts each prompt's tokens from its characters at 2.5 a token, and each reply at its token limit, thinking included. Legal text tokenizes finer than English prose: the first batch's prompts ran 2.77 characters a token (8.67 million characters, 3,134,052 input tokens), so 2.5 errs high where the 3.5 first assumed fell short. With `--live`, a run projected over `--max-cost`, $10 by default, is refused before anything is sent. `--batch` sends every pair in one request to the Batches API, at half the price; the command waits for it to end, polling once a minute, and `--batch-id` collects one already sent. Each request asks at low effort with a limit of 1,024 tokens, enough for a label's thinking and its reply; a reply cut off at the limit, declined or off the schema is unusable, counted and left for the next run. Batches take no server-side fallback, so a declined pair stays unlabeled rather than going to another model. Each batch's tokens and cost are read back from its results and recorded in `reports/label_spend.json`, and a run is refused when what is spent and what it is projected to cost together pass `--budget`, $30, the cap set for the precision labels. The 300 drawn pairs cost $6.30, at 3,115 output tokens across all 300 replies: at low effort the model gave each label with almost no thinking. `--prompt` names what is asked: `v1`, the sections at low effort; `v1-high`, the same at high effort with a limit of 4,096 tokens; `relatives-v1` and `relatives-v1-high`, the 0–4 scale on a relative's passages, drafted for the page samples and never asked; and `passages-v1-high`, the passage-level question below, with a limit of 2,048 tokens. That limit was set when the one batch the review asked for was projected at $23.04 at 4,096, which with $7.22 spent would have passed the budget. At high effort the section prompt's replies had averaged 134 tokens. `--also SAMPLE=LABELS` asks several samples in one batch, each labeled into its own file. The passage-level batch labeled the first two page samples and the flag's 102 dropped pairs, 302 pairs, with no unusable reply, for $9.71: 4,700,468 input and 31,248 output tokens (`reports/label_spend.json`). The second Georgia sample, drawn at 0.93, took one more batch, 100 pairs with no unusable reply, for $1.13: 529,020 input and 7,561 output tokens. The reporting sample, drawn at 0.94, took another, 100 pairs with no unusable reply, for $2.12: 1,018,082 input and 8,411 output tokens, since its pages' sections run longer. All the precision labels together cost $20.19 of the $30. Each is its own labeler, so labels asked under one are never mixed with another's (`uv run lineage eval precision --model-labeler`). Model labels give precision an estimate before volunteers have labeled; they are never pooled with people's.

**Checking the model's labels.** A model's labels stand as provisional only once a person has checked them. `uv run lineage agreement-sample` draws 50 of the 300 labeled pairs, 17 found by the near-duplicate stage alone, 17 by the semantic stage alone and 16 by both, under a fixed seed, into `evals/agreement_sample.jsonl`, with the precision sample's own rows and pair ids. A person labels them with `lineage label` as above, blind to the stages and to the model's labels. `uv run lineage eval agreement` then compares the two where both labeled: Cohen's weighted kappa on the 0–4 scale, with linear weights, and the share of pairs on the same side of the correct/incorrect cutoff. Linear rather than quadratic weights, because quadratic ones discount a one-step disagreement most, and a one-step disagreement across the cutoff is the one precision turns on. The bars were set before any person labeled: kappa of at least 0.6 and cutoff agreement of at least 85%. Short of either, the same 50 pairs are labeled again by the model at higher effort and compared again; if that still falls short, precision rests on people's labels alone.

**What the check found, and what was decided.** A person labeled the 50 pairs blind, with copied and paraphrased text highlighted (`uv run lineage eval agreement` → `reports/results.json`, `label_agreement`). At low effort (`v1`) the model reached a weighted kappa of 0.41 and cutoff agreement of 76.0% [62.6, 85.7]. Each of its 12 disagreements across the cutoff was a pair the person called related or closer and the model called a shared subject with different provisions. At high effort (`v1-high`) it reached a kappa of 0.50 and cutoff agreement of 94.0% [83.8, 97.9]. Kappa fell short of its bar at both efforts, so by the rule set beforehand the model's labels do not stand. At review the decision was to use them anyway, for four reasons:

- Kappa failed on how similar a related pair is, which precision does not use: on 14 pairs the person said almost identical and the model related.
- Every one of the three disagreements left across the cutoff had the model lower than the person, so a precision from its labels reads as a floor. On the same 50 pairs, weighted by the build's strata as the precision sample is, the person's labels give 0.75 [0.58, 0.82], the model's at high effort 0.65 [0.50, 0.74], and at low effort 0.52 [0.39, 0.65] (`precision_on_these_pairs`).
- The person's labels are a non-expert's, given with copied text highlighted, which the model never saw.
- Labels that settle the question would need legal expertise, which is beyond this project's scope.

So every precision reported here is model-judged, with this check beside it. People with legal training can add labels ([CONTRIBUTING.md](CONTRIBUTING.md#labeling-matches)). Theirs are estimated apart from the model's and never pooled with them.

**The passage-level question, added 2026-11-11.** The 50 pairs also showed that the section-level question has no clear answer when one section holds the other plus more: the person and the model disagreed most on how closely such a pair is related. What a page claims is narrower, that the passages it highlights state the same provision. So from here the model is asked that directly (`--prompt passages-v1-high`). It sees the passages the alignment matched ([Alignment](#alignment)), not marked as copied or paraphrased, with both sections for context, and answers yes or no: do these passages state the same provision, beyond boilerplate? When the alignment matched nothing, it answers for the sections whole. A yes is recorded as label 1 under `"scale": "same_provision"`, so it is never read on the 0–4 scale, and only a yes counts as correct. The question is asked at high effort, the effort at which the check was met on the cutoff, but this prompt has not itself been checked against a person.

The weighted interval adds two successes and two failures to each stratum before summing the variances by weight (Agresti and Coull), so a stratum labeled all correct still has an interval of some width. A weighted estimate is left out until every stratum it covers has a label. Where a person and the model both labeled a pair, the report counts how often they gave the same label and how often they agreed on whether the match is correct.

## Explanations

For featured matches, a model summarizes what changed between the origin and the descendant. Besides the provisional precision labels, it is the pipeline's only model call, and its replies are cached so a keyless run can replay them.

**Input and output.** The model sees the aligned spans with their ids ([Alignment](#alignment)), not the raw bill texts, so it sees exactly what is shared and what differs. Its reply must fit one Pydantic class, `ChangeExplanation`: at most four claims, each a kind (added, removed or changed), a summary of at most 200 characters, and the ids of the spans it cites on the origin's side and the descendant's (`lineage.explanations`). The same class gives the JSON schema sent to the model and validates the reply.

**Differences, not direction (ruled 2026-11-12).** An explanation describes how each text differs from the origin's text, never what a state changed or copied. "Origin" names the text a featured story's comparison starts from, and "descendant" the other one. Neither story's origin is a documented source. The commission drafted the anti-SLAPP act, and its origin here is the earliest enacted state version. Washington SB 5152 is an anchor, not a source. So no claim may say which text came first or who drew on whom. The prompt says so, and the faithfulness judge counts a claim that implies direction as not describing its spans correctly.

**The featured scope (ruled 2026-11-12).** `uv run lineage featured` writes the pairs explained, every section pair a page lists between a story's anchor and each of its relatives, the anchor's section as the origin (`lineage.featured` → `evals/featured_pairs.jsonl`, `reports/featured_pairs.json`). The anti-SLAPP story's anchor is Utah SB 18 of 2023, signed 2023-03-23, the earliest enacted state version of the commission's act in the corpus. Its relatives are the bills the commission's lists name as enacting the act, and it has 56 pairs with 21 of them. The act's own text stays a local eval query and is never shown. Six of those bills share no listed pair with Utah: Oregon's, Maine's and Pennsylvania's two enactments have none at all, and Iowa's HF 472 and Missouri's SB 835 are companions of bills that do. The site still shows every enactment, found against the act, with an explanation only where a Utah pair exists. The deepfake story's anchor is Washington SB 5152 of 2023–24, with 46 pairs among the 40 relatives its page lists that were introduced after it. The Georgia story's anchor is SB 351 of 2023–24, the Protecting Georgia's Children on Social Media Act, with 35 pairs among the 27 relatives its page lists. That is 137 pairs in all.

**Grounding is checked in code.** A claim is kept only if it cites at least one span, every id it cites is a span of this alignment with text on the side it is cited for, none is an exact copy, and none reads the same on both sides once normalized, since neither is a change. A failing claim is dropped with its reason. The check reads each span by its id, its kind and the SHA-256 of each side's normalized text (`lineage.explanations.GroundingSpan`), so it runs the same on a live alignment and on a cached reply with no bill text at hand. The span check guarantees that every claim points at a real difference; whether its summary is true of that difference is the faithfulness eval's question.

**Calls.** `uv run lineage explain PAIRS --live` asks `claude-opus-5-5` through the Anthropic SDK, with structured output from the same class, effort `medium`, a limit of 4,096 output tokens, and the API's server-side fallback for a declined request, so the cache records which model served each reply (`lineage.explain`). The key comes from `ANTHROPIC_API_KEY`. The pairs file is the scope, the featured stories only. Nothing here is agentic: one request per pair, and not batched, since the Batches API does not offer the fallback.

**Retry and withholding.** A failing claim is dropped and the rest are kept. A reply is unusable when it is declined, does not fit the schema, or makes claims none of which is grounded; an unusable reply is asked again once, and if the retry is unusable too, the explanation is withheld. A reply with no claims says nothing of substance changed, and is kept as such. A withheld explanation is shown as nothing: the comparison view then shows the alignment alone.

**Cache.** Every outcome, a withheld one included, is stored under the SHA-256 of the model id, the prompt version and the spans, in `explanations/cache/`, which is committed. A rerun pays only for pairs it has not seen; keyless users replay the cache; a changed prompt or alignment changes the key, so a stale answer cannot be served. A cached reply is grounded again each time it is read. Without `--live`, a pair with no cached outcome is an error, never a call. A cache file holds no bill text: beside the reply it keeps each span's grounding form and which claims grounding kept and dropped, and why.

**Budget.** Every M6 model call, explanations and the faithfulness judge together, is held to $30, the cap the M5 review set for the featured scope (`lineage.spend` → `reports/explanation_spend.json`). Before anything is sent, a run is projected at most: each prompt's tokens from its characters at 2.5 a token, each reply at its token limit, each asked as often as it may be retried. It is refused when that and what is spent pass $30. Each call's tokens are recorded as it returns, and before each call the same bound is checked for that call alone, so the ledger cannot pass the cap however a run goes.

**The hard check, in CI.** `tests/test_explanation_cache.py` grounds every committed explanation again from what its file records (`lineage.explain.check_cache`): each kept claim must cite spans that exist and differ between the two texts, the record of what was kept must be what grounding gives now, and no reply whose claims all fail may be kept. It needs no corpus, so CI runs it on every push.

**Faithfulness, model-judged.** The hard check guarantees that every kept claim cites a real difference; whether its summary is true of that difference is judged by a model, as the M5 review ruled in place of labeling about 25 pairs by hand. `uv run lineage eval faithfulness PAIRS --live` asks `claude-opus-5-5`, at medium effort with a limit of 1,024 output tokens, one claim at a time: it sees the claim's kind and summary and the text of each span it cites, on the side it cites it, and nothing else, and answers through structured output whether the claim describes those spans correctly (`lineage.faithfulness`, prompt `judge-v1`). A correct claim's kind fits its spans and everything its summary asserts is borne out by them. A verdict is keyed by the explanation's cache key, the claim's position and a hash of the claim with its spans' grounding form, so a regenerated explanation is never scored by an old verdict. Verdicts go to `evals/faithfulness_judgments.jsonl`, which holds no text, and a rerun asks only for claims not yet judged. A declined or malformed reply is asked again once, then counted apart as unusable. The eval reports the share judged correct with a 95% Wilson interval, overall and by kind, beside what grounding did: explanations, withheld ones, and claims kept and dropped by reason (`reports/results.json`, `faithfulness`). The judge is the same model that wrote the claims, prompted only to check them, and no person checks it, so the share is reported as model-judged, as precision is.

| Alternative | Reason rejected | Evidence |
|---|---|---|
| Compare all pairs | Quadratic in the number of sections: about 5.1 × 10¹² pairs at the measured *N* | Arithmetic on the measured section count |
| Embeddings only | No exact-span evidence to highlight, a higher cost per section, and less precise: on a Georgia page, what meaning alone finds is right less often than what shares wording | Recall does not settle it: alone, the semantic stage finds the same 33 of 36 development enactments as both stages, and the same 17 of 19 held-out ones (`reports/results.json`, `stage_ablation`). Precision does, model-judged on the reporting sample at 0.94: of the relatives a Georgia page lists, 0.90 [0.79, 0.96] of those sharing wording are right, against 0.75 [0.61, 0.85] of those found by meaning alone. The near-duplicate stage alone found 27 of the 100, 24 of them right, which embeddings alone would not list (`uv run lineage eval relatives` → `relatives_precision`). Model-judged: on the 50 pairs a person checked, the model's labels gave 0.65 where the person's gave 0.75 ([Precision sample](#precision-sample)) |
| Embeddings as a reranker of LSH candidates | A reranker can only reorder pairs LSH already proposed, so it can never recover a paraphrase LSH missed | Follows from the design |
| Whole bills as the unit | Dilutes provisions carried inside omnibus bills | Commission-recall misses show the cost at a smaller scale: a bill split into a few chapter-sized sections is never proposed against the act's short ones (`reports/results.json`, each bill's `signed_sections` and `stage`) |
| LSH Ensemble: search by containment directly, with sets partitioned by size and each partition banded for the containment threshold | Windows recover containment with the MinHash signatures, banding and verification unchanged, and they are the units the semantic stage embeds, so both stages name the same units. LSH Ensemble would add a second index design with per-partition band settings, a containment threshold chosen per query, and still leave the semantic stage needing units that fit a model. What windows cost is rows: 16,671,477 windows where there were 2,873,256 sections, 5.8 times, and signatures and band index of 8.54 and 6.40 GB where whole sections took 1.49 and 1.12 GB, with the build's time and memory growing in step ([Scaling limits](#scaling-limits)) | `reports/index.json` (`windows`, `signature_bytes`, `lsh.index_bytes`, `build`), and the same file as committed with whole sections (d0ecae8) |
| Scope the corpus by topic keywords | Makes recall circular, since only bills that match the keywords can be found, and it removes the hard negatives | Follows from the design |
| LLM calls or a hosted vector database in retrieval | Breaks the keyless and static constraints | Constraint |
| A query server behind the site | Breaks the static constraint | Constraint |
| Smith-Waterman alignment for highlighting | Gap scoring adds nothing to marking shared blocks; `difflib` finds them from the standard library | Follows from the design |
| LegiScan as the text source | Its [terms of service](https://legiscan.com/terms-of-service) restrict copying, which conflicts with publishing excerpts | Sourced |

## Scaling limits

The window count sets the size of everything downstream. The 16,671,477 signed windows' MinHash signatures take 8.54 GB, and their band index 6.40 GB (`uv run lineage index` → `reports/index.json`, `signature_bytes` and `lsh.index_bytes`). That is 5.8 times what whole sections took, the cost of comparing long sections window by window ([Windows](#windows)). On the reference laptop, with 32 GiB of memory, the build takes 2,145 s and peaks at a physical footprint of 7.98 GiB (`build`), within the 16 GiB bound [DR-3](#dr-3) sets. It holds neither the signatures nor the band index in memory: both are files it memory-maps, and it forms candidates one band at a time, verifying each as its first band forms it. What it holds is the set of candidates seen so far, 8 bytes each, and the verified pairs. Ten times the corpus means about 150 GB of signatures and band index to read from disk, and that set of candidates grows with it.

| Pressure | What breaks first at 10× | Response |
|---|---|---|
| Index size | Signatures and embeddings outgrow memory, and the set of candidates seen grows with them | Signatures and band index are already memory-mapped; shard by state and session, and merge the sorted LSH keys per shard |
| New sessions | A full rebuild for every update | Append only: hash and embed the new sections, then recompute neighbors only for bills that share a bucket or neighbor with them |
| Formatting noise | More state-specific markup, scanned images, and struck-and-inserted amendment text | Per-state normalizers behind one interface, each with fixture tests, and extraction errors tracked per state |
| Duplicate versions | With full version history, a bill's own versions crowd out other states | Collapse versions into one family before scoring, as companion bills already are |
| Boilerplate | The shared-clause load grows with the corpus | Recompute the document-frequency stoplist each build, and watch the LSH bucket-cap counter |
| Hosting | One file per bill for all states exceeds static-host limits | One export per state, or a sharded layout on object storage |

### DR-1 · Front end: Next.js static export

**Status:** accepted, 2026-11-05.

**Context.** The hosted site is a set of read-only views over precomputed JSON: a landing page, featured stories with a state tile map and a timeline, a side-by-side comparison with highlighted spans, a browse page that filters the hosted state's bill list in the browser, a page per bill, and validation and baseline pages. Nothing may run server-side. Several views are interactive, so some client-side code ships whatever the framework. The data contract is the JSON that `lineage export` writes, with its schema emitted by the Pydantic models that produce it.

**Options.**

- **Next.js with `output: "export"`.** React components, file-based routing, and per-bill pages generated at build time from the exported bill list. Static export gives up server features (route handlers, on-demand revalidation, image optimization) that this site has no use for. The cost is that every page ships the React runtime.
- **Astro.** Ships no JavaScript by default and hydrates interactive islands on their own. Pages would be lighter. But the comparison and browse views still need a component framework inside their islands, so the project would carry two component models instead of one.
- **Python templating (Jinja) into plain HTML.** Keeps one language. The interactive views would become hand-written JavaScript with nothing checking them against the JSON contract, which is where schema drift between pipeline and site would surface as runtime bugs.
- **Streamlit or a dashboard framework.** Needs a running server, which breaks the static constraint, and presents an internal-tool look to a public audience.

**Decision.** Next.js static export in TypeScript, for three technical reasons:

- **Pre-rendering at scale.** Static export renders every hosted bill's page at build time from the exported bill list, so thousands of pages ship as plain files with nothing running server-side.
- **One data contract.** The Pydantic models that write the export also emit its JSON Schema, and the site's TypeScript types are generated from that schema. The pipeline and the site therefore share one definition of every field.
- **Interactive views in one component model.** React components carry the state tile map, the timeline, the highlighted comparison and the browse filter.

Existing team expertise with Next.js is a secondary, maintainability factor: it lowers the cost of keeping the front end current.

**Consequences.**

- The Python side owns the schema, and the site consumes it as generated types. A breaking change to the export fails the site's type check, not a user's browser.
- The repo carries two toolchains, uv and npm. CI gains a front-end job in M7.
- Build time and output size grow with the number of hosted bills. Both are measured in M7.
- Every page pays for the React runtime. Page weight is measured in M7 and reported.

**Would reverse it.** If page weight on the bill or comparison page breaks the budget set for phones on slow connections in M7, the presentation layer moves to Astro. The JSON contract and the generated types carry over unchanged, so only the presentation layer would be rewritten.

### DR-2 · Host: GitHub Pages

**Status:** accepted, 2026-11-05.

**Context.** The site is static files, one JSON file per hosted bill plus a few aggregate files. File count and total size are the binding constraints. The build runs in this repository's CI, so the deploy should need no credentials beyond what that CI already has.

**Options.**

- **GitHub Pages**, deployed by this repo's Actions with `actions/deploy-pages`. The deploy authenticates with the workflow's own short-lived token, so the project holds no secrets or external accounts. GitHub [documents](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) a 1 GB limit on a published site and a soft bandwidth limit. Response headers cannot be customized.
- **Cloudflare Pages.** A faster edge and configurable headers. Its free plan caps a site at 20,000 files ([limits](https://developers.cloudflare.com/pages/platform/limits/)), so one file per bill leaves little headroom even for one state, and it needs an external account plus a deploy token stored as a repo secret.
- **Netlify or Vercel.** Comparable to Cloudflare, with the same external-account and secret cost.
- **Object storage (R2 or S3) behind a CDN.** No practical file or size limits, but it needs a custom domain, bucket configuration and credentials, which is more moving parts than a single-state site needs.

**Decision.** GitHub Pages, deployed from this repository's workflow.

**Consequences.**

- No secrets: the deploy job requests the `pages: write` and `id-token: write` permissions on its own job and nothing more.
- The 1 GB limit holds the hosted site to one state. Hosting more states is out of scope for this host.
- The site is served under `/<repo>/`, so the Next.js `basePath` must match.
- Caching headers are GitHub's defaults. JSON is small and per-bill, so this costs little.

**Would reverse it.** If the hosted state's export exceeds about half the 1 GB limit (measured in M7), which leaves too little room for growth, or if hosting more than one state becomes a goal. The response is the sharded object-storage layout in [Scaling limits](#scaling-limits).

### DR-3 · MinHash engine: an own NumPy implementation, with datasketch as the test oracle

**Status:** decided, 2026-11-05. The step 11 measurement met the reversal criterion as first written. That criterion left out two requirements, and against the completed criterion the decision stands. Signing sections by window first took a full build over the 16 GiB memory bound, and verifying band by band against memory-mapped signatures brought it back within it ([Windows and the memory bound](#windows-and-the-memory-bound)). Both versions of the criterion are below.

**Context.** The near-duplicate stage signs every section in the corpus and buckets the signatures by LSH band. The hot paths are hashing each shingle under every permutation, taking the minimum per permutation, hashing each band to a key, and grouping equal keys. At corpus scale, any per-element Python work in those loops dominates runtime and memory. The implementation also has to be simple enough to verify by reading.

**Options.**

- **[datasketch](https://github.com/ekzhu/datasketch).** Mature and widely used. Its batch path (`MinHash.bulk`, `update_batch`, and `MinHashLSH.insertion_session` for buffered inserts) avoids per-shingle Python loops. It still represents each set as a Python object and stores LSH buckets in dict-backed storage, so per-object overhead and the memory of millions of buckets are the costs to measure.
- **An own NumPy implementation.** Signatures form one dense unsigned-integer matrix with one row per section. Shingles are hashed once to 32 bits, and each permutation is a universal hash (*a*·*x* + *b*) mod *p*, applied to all shingles in a single vectorized operation. Band keys are hashed to 64 bits, and candidate pairs come from sorting the keys and reading off runs of equal values, not from a dict.
- **A compiled third-party MinHash library** with Rust or C++ bindings. Likely the fastest, but it adds a binary dependency and hides the algorithm behind bindings that can't be read or tested line by line.
- **A distributed engine (Spark).** Solves a scale this corpus doesn't have, and needs a cluster.
- **A hybrid:** datasketch's signing feeding this project's band index. Weighed after step 11, below.

**Decision.** An own NumPy implementation. datasketch stays as a development-only dependency and serves as the test oracle: on the same inputs and parameters, both must produce agreeing similarity estimates.

**The criterion as first written.** It named two binding constraints. The full corpus must be signed within an overnight run, and the LSH index must fit in memory, both on the reference laptop. That is the machine the benchmarks run on, and each benchmark output records its CPU, core count and memory. Fitting in memory means that a full index build, signatures plus LSH index, peaks within 16 GiB, half of the reference laptop's 32 GiB, leaving the rest for the operating system and the later stages. The bound was fixed before the index was measured. The criterion read:

> If, on the reference laptop, datasketch builds signatures for the full corpus within an overnight run (eight hours of wall-clock time) *and* its LSH index fits in memory, then datasketch meets the constraints that justified owning the code, and it becomes the engine. A raw speed ratio is not the test: a slower library that meets both constraints is still the cheaper thing to maintain.

The benchmark puts both engines through the same work. It runs datasketch through its batch path, never a per-shingle loop, so the comparison is with the library at its best. It records wall-clock time and peak memory for building the signatures and the LSH index, on the full corpus.

**Measured in step 10** (`uv run python -m benchmarks.minhash` → `reports/minhash_benchmark.json`; Apple M1 Max, 10 cores, 32 GiB). The comparison concerns cost per section, so it is re-run when the corpus changes by more than 5%. Step 10's run gave each engine one core and the same 1,916,250 stoplisted sections. Splitting at citation headings later raised the signed sections to 2,058,712, 7.4% more, so the benchmark was re-run on them (`git show 7d2ab87:reports/minhash_benchmark.json`). Fetching bill text from the legislatures ([DR-6](#dr-6)) then raised them to 2,898,515, 40.8% more, and it was re-run again on those, 701,857,057 shingles in all (`engines.numpy.sections` in the report). The figures below are from that run. Step 10's report is in git history (`git show 714f085:reports/minhash_benchmark.json`). Signing time per million shingles has stayed within 4% across the three runs, so the times grow with the corpus and the ratio between the engines holds.

- **Signing time.** The NumPy implementation took 397 s and datasketch 150 s. The context above expected per-element Python work to dominate datasketch's time. On this corpus it does not.
- **Signature memory.** The NumPy matrix holds 512 bytes per section and datasketch's objects 785 (`tracemalloc`, on a 20,000-section sample), or 1.48 GB against 2.27 GB for the corpus.

**Why signing is slower here.** The cost is the permutation arithmetic, not data layout. datasketch 2.0's default scheme computes *a*·*x* + *b* in wrapping 32-bit integers: two array operations on 4-byte values for each shingle and permutation. The exact (*a*·*x* + *b*) mod *p* takes about sixteen operations on 8-byte values (`minhash._hash_into`), and NumPy runs each as a separate pass over the run's arrays. A profile on one core found that hash to be nearly all of the signing time, and changing the run length or removing the two temporary arrays it allocates did not change the time materially. No small fix remains. Fusing the passes needs compiled code, which the options above rejected. A multiply-add modulo 2<sup>32</sup> would change every stored signature, and its accuracy would rest on empirical tests rather than on the pairwise independence of the mod-*p* family. Signing runs once per snapshot, in parallel, so the gap is left as it is.

**Measured in step 11** (same command; the report as of `714f085`). Each engine built its index of 32 bands × 4 rows in a fresh process from the stored signatures table, loaded into memory. datasketch inserted every row of the 1,916,250 through `MinHashLSH.insertion_session`, under a watchdog that would have stopped the build at the memory bound or the disk floor. It did not stop.

- **Peak memory.** NumPy peaked at 2.1 GiB and datasketch at 15.3 GiB, 0.7 GiB inside the 16 GiB bound. Peak memory is the process's physical footprint, which on macOS includes compressed pages that the resident set size leaves out.
- **Index memory.** The index added 0.66 GiB with NumPy, its two dense matrices, and 14.3 GiB with datasketch, about 8 KB per section in dictionaries of byte strings and sets.
- **Build time.** 10 s and 571 s.

datasketch therefore met both conditions of the criterion as first written, with 4% of the memory bound to spare.

**The re-runs** (`reports/minhash_benchmark.json`, `lsh`). On the 2,898,515 sections of the current corpus, datasketch reached the 16 GiB bound after inserting 2,000,000, holding 14.6 GiB of index, and the watchdog stopped it, as it had on the 2,058,712 of the first re-run. NumPy built the whole index in 18.8 s, adding 0.98 GiB, at a peak of 3.1 GiB. On the current corpus, datasketch fails even the criterion as first written.

**The criterion was incomplete.** It left out two requirements that the project's plan had set before the benchmark ran, though this document did not state them until now ([Constraints](#constraints)). The prebuilt index ships as release assets, each under GitHub's 2 GiB per-file limit. `lineage query` runs offline on a user's laptop after one download of those assets. Both were added to the criterion after the step 11 result was known. That is the kind of after-the-fact change that fixing the memory bound in advance was meant to rule out, so it is stated here for the reader to weigh.

**Against the full criterion, datasketch fails.**

- Its index is 14.3 GiB of Python dictionaries inside the building process. It has no file format and cannot be memory-mapped, so every query would first have to bring all of it into memory, whether by loading a serialized copy split across release assets or by rebuilding it.
- Rebuilding it on the user's machine from the signatures took 571 s on the reference laptop in step 11 and peaked at 15.3 GiB, more than a laptop with 16 GiB of memory can hold.
- The 4% of headroom that step 11 left on the reference laptop was gone after 7.4% more sections.

This project's index is two `.npy` matrices. Signed by section they took 1.11 GB, each under the limit; signed by window they take 6.40 GB (`reports/index.json`, `lsh.index_bytes`), and the keys matrix alone outgrows one asset, so the release splits it into assets under the limit. A query memory-maps them and reads only the pages its keys land on.

<a id="windows-and-the-memory-bound"></a>
**Windows and the memory bound.** Signing by window ([Windows](#windows)) multiplied the rows 5.8 times. On the reference laptop, the full build's main process, which holds every signature while it bands and verifies them, peaked at a physical footprint of 20.7 GiB, over the 16 GiB bound, though within the machine. The engine was not the cause: signing runs in worker processes that each peak under 2 GiB. The build held every signature and every candidate pair in memory at once. It now writes the band index to memory-mapped files, forms candidates one band at a time, drops those an earlier band formed, and verifies the rest against the memory-mapped signatures, so it holds only the codes of the candidates seen and the verified pairs. The full build peaks at 7.98 GiB and takes 2,145 s, against 2,115 s before, with every count in its report unchanged (`uv run lineage index` → `reports/index.json`, `build`). Memory-mapped files are not part of the physical footprint, but they still need memory to be read quickly: the build reads the band index in order, and the operating system keeps the signatures that verification reads at random in its page cache, with the build's time unchanged. An earlier version also kept the cap sweep's per-row table in a memory-mapped file written at random; under the same memory pressure it ran for hours without finishing. The sweep now gathers only the rows its pairs need, in memory.

**The hybrid, rejected.** datasketch's signing feeding this project's band index would meet the full criterion. It would save at most the 246 s of single-core signing time that the latest run measured, less once spread over the worker processes of a build that runs once per snapshot. In exchange, datasketch would become a runtime dependency rather than a test oracle, and the signatures would depend on its hash scheme staying fixed across releases.

**Consequences.**

- Correctness is this project's to own. The oracle test and the S-curve test of the empirical candidate rate are what make that acceptable.
- A dense signature matrix memory-maps and shards without conversion, which is the first response to [index growth](#scaling-limits).
- Sorting to bucket costs *O*(*n* log *n*) with predictable memory, where dict buckets fragment the heap.
- Time and peak memory for both engines are a recorded measurement, not an assumption. The benchmark stays, so the comparison can be rerun on a new snapshot or a new datasketch release.

**Would reverse it.** Revisit this decision if a maintained library offers a persistent LSH index that memory-maps and that a full build produces within the 16 GiB bound, or if the offline query path is dropped. If the NumPy implementation itself misses the overnight or memory bound, a compiled library replaces it. In either case the oracle tests carry over.

### DR-4 · Data tooling: DuckDB over Parquet

**Status:** accepted, 2026-11-05.

**Context.** The input is Open States' per-session JSON for 50 states across four years: 220 archives, 6.42 GiB (`uv run lineage snapshot`, `snapshot/manifest.json`). The transformations are relational: flatten nested actions and versions, derive status, filter, and aggregate per state and session for coverage statistics. Their outputs feed NumPy, for hashing and embedding, and the exporter. Everything runs on a laptop and has to work when the data does not fit in memory.

**Options.**

- **pandas.** Ubiquitous, but eager and in-memory. Normalizing nested JSON is awkward, and object-dtype columns are weakly typed under a strict type checker.
- **Polars.** Fast, lazy, able to stream larger-than-memory data, and well typed. A close second.
- **DuckDB.** Reads nested JSON in place with SQL (`read_json`, `unnest`), spills to disk when memory runs short, writes Parquet natively, and hands columns to NumPy through Arrow without copying. Its CLI makes the intermediate tables easy to inspect directly.
- **SQLite.** A row store with no native Parquet or JSON-array handling. Aggregations over the full corpus would be slow.
- **The standard library's `json` module with Python loops.** The simplest option, but slow and memory-heavy at corpus scale.

**Decision.** DuckDB reads the raw JSON and writes Parquet tables (`bills`, `sections`). Relational work stays in SQL, and numeric work moves to NumPy through Arrow.

**Consequences.**

- Parquet is the interchange format between pipeline stages, readable by any tool. A stage can be rewritten without touching its neighbors.
- SQL inside Python strings is invisible to pyright. Queries live in one module, run against committed fixtures in tests, and their result schemas are checked where they enter typed code.
- The choice over Polars is a judgment, not a measurement: reading nested JSON with SQL and inspecting tables in the CLI outweighed Polars' typed expression API.

**Would reverse it.** If DuckDB's JSON reader cannot handle the snapshot's shape or size without per-file Python preprocessing, which step 4 finds out, a streaming Python reader writes the Parquet and DuckDB keeps the queries. If most transforms turn out to need row-wise Python functions, Polars replaces DuckDB.

### DR-5 · Match only document types that can carry law

**Status:** accepted, 2026-11-05. The type lists and per-state rules were set from the step 8 counts.

**Context.** An Open States session archive holds every measure a legislature filed, not just bills. It includes resolutions, proclamations, appointments, nominations, memorials and commemorations. Commemorative measures are numerous and highly formulaic ("commending", "recognizing", "expressing condolences"), so they flood the near-duplicate stage with matches on text no one is tracing. Type labels also vary by state, and a generic label can hide both kinds of record. Georgia, for example, files proposed constitutional amendments and commendations alike as "resolution", and its titles carry the distinction instead: a trailing "; commend" or "; recognize" against "; provide - CA". So a single global allowlist of types would either drop substantive measures or admit commemorations.

**Options.**

- **Match everything.** No record is lost, but commemorative boilerplate dominates the candidate pairs and the precision sample, and the stoplist ends up working around document types instead of legal boilerplate.
- **Match only records labeled `bill`.** Simple, but it drops substantive measures that states file under other labels, such as constitutional amendments and joint resolutions with the force of law.
- **Per-state rules over document type.** A default list of types eligible for matching, with per-state overrides where a state's labels don't separate law from ceremony. An override may use that state's own title convention, as in Georgia. Commemorative and memorial measures are always excluded.
- **A topic or keyword filter.** Rejected: it would make commission recall circular, since only bills that match the keywords could be found, and it would remove the unrelated bills that test precision.
- **A model classifying each record.** Rejected: it puts a model call in the retrieval path, which breaks the keyless constraint.

**Decision.** Per-state rules over document type, in one committed table, `rules/document_types.csv`. Rules are read top to bottom and the first that fits a record decides it. `lineage eligible` applies them and counts every rule's records per state in `reports/document_types.json`.

- **Matched by default:** bills, appropriation bills, proposed bills, joint resolutions, and records classified as constitutional amendments. Joint resolutions stay in because many states use them to propose constitutional amendments, and some give them the force of law.
- **Excluded by default:** simple and concurrent resolutions, memorials, commemorations, proclamations, appointments, nominations and study requests. They are formula-heavy: commendations, condolences, requests to Congress, and procedural motions written to a few templates. Matched, they would crowd every bill page with relatives that share only those templates, and their formulas would claim stoplist slots meant for legal boilerplate.
- **Per-state exceptions** admit constitutional amendments that a state files under an excluded type, by that state's title convention: New Jersey's and Mississippi's concurrent resolutions that propose amending the constitution, and Georgia's resolutions whose titles end in "-CA". Each is a row of the table, and the report gives its count.
- **Commemorative joint resolutions** are excluded by a title pattern. The title must open, after any type prefix, with commending, commemorating, congratulating, honoring, paying tribute, recognizing, celebrating or mourning. A title that names a constitution, an amendment, a proposal, a right or a law is spared. The report counts the titles each rule excluded and spared, per state, and `lineage stats --samples` lists them locally, so false positives in both directions can be checked. Tennessee files every memorial as a joint resolution titled "Memorials, <occasion> - <honoree> -", for recognitions, deaths, retirements, academic and sports achievements, interns and petitions to Congress alike. Those titles name the occasion rather than opening with a verb, and an honoree's name or cause can carry a word the guard reads as law, so a Tennessee row excludes the prefix with no guard. It was found when 830 graduation memorials formed the corpus's largest family. "Memorials, Congress" titles call on Congress, so they are kept.
- **Commemorative and procedural joint resolutions** are excluded whatever their wording, by one row per kind: namings of highways, bridges and roads; designations of a day, week, month or year; confirmations of appointees; adjournments, recesses, joint sessions and conventions, joint rules and joint orders; and claims against the state. A joint resolution that expresses a position or calls on Congress is kept, and so is one that proposes changing the process it names, such as a constitutional amendment on confirmations. Each row's guard says what it spares.
- **Title rules apply only to joint resolutions and to the per-state exceptions.** Bills are never excluded by title: a bill naming a bridge or designating a day is still law.

**Counts** (`uv run lineage eligible` → `reports/document_types.json`). 78,244 of 525,633 records are excluded: 53,165 simple resolutions, 9,470 concurrent resolutions, 5,783 Tennessee memorials filed as joint resolutions, 2,265 proclamations, 1,635 appointments, 1,546 other commemorative joint resolutions, 780 memorials of the three kinds, 423 nominations, 188 commemorations and 24 study requests. Of joint resolutions, 1,074 designate an observance, 701 decide claims against the state, 602 confirm appointees, 357 are procedural and 231 name a road or bridge. The exceptions admit 451 New Jersey concurrent resolutions, 122 Mississippi concurrent resolutions and 102 Georgia resolutions. No record has a type the table doesn't list.

The filter does not bias the recall eval. It selects on what kind of document a record is, independent of its subject, so it removes records that aren't law without regard to any story or act. The unrelated bills on every topic, which are the hard negatives that test precision, all remain.

**Consequences.**

- Excluded records stay in `bills` with their classification, and the filter is applied downstream (`data/tables/eligible.parquet`). Changing a rule means editing the table and rerunning `lineage eligible` and `lineage boilerplate`, with no re-ingest. The choice is reversible by configuration.
- The stoplist is counted over matchable sections only, so the excluded types can't shift it.
- A substantive measure filed under an excluded type can't be found. The recall eval reports "excluded type" as a distinct miss reason, so such a loss shows up rather than hiding inside "not found".
- Known gap: Nebraska's, Michigan's and Rhode Island's resolutions include constitution-titled records whose conventions are not yet checked, so they stay excluded. Each is admitted by a rule once its convention is checked and its count measured.

**Would reverse it.** If the recall eval shows any listed enactment lost to "excluded type", the rule that excluded it is revised. If the precision sample shows commemorative text still producing matches, the rules widen. The exclusion of resolutions as a whole is reopened when a user wants to trace resolution campaigns, such as the same request to Congress filed in many states. That use needs the excluded types matched as their own corpus, not mixed into bill pages.

### DR-6 · Own the text layer

**Status:** accepted, 2026-11-07. The quality test (`reports/text_quality.json`) decided which states, formats and PDF readings are fetched, and the full fetch (`reports/text_fetch.json`) and both recall runs measured the result.

**Context.** Open States' bulk export carries each bill's text as extracted by its scrapers. For 145,946 of 447,389 eligible records the text is unusable (`reports/text_inventory.json`): blank for 129,633, absent for 8,708, an amendment in place of the bill for 5,442. The gap is not three states, as first assumed. It covers whole sessions (Hawaii 2024 and 2025, Virginia 2025 and 2026, Massachusetts's 193rd) and most records of New Jersey, Maryland and Montana. A record with no text cannot match anything, so recall over the corpus is capped by upstream extraction. The export does keep the links to every version of each bill, on the legislatures' own sites.

**Options.**
- Wait for upstream. The gap moves with each scrape and has no error flag, and the project would inherit every regression.
- Run Open States' scrapers. They also scrape bills, votes and people, need per-state configuration, and their code is GPL-3.0, which cannot be imported into this MIT repository. Reading their extraction for reference is fine.
- Fetch and extract the linked versions ourselves, per state where needed.

**Decision.** Own the text, not the metadata. Open States stays the source of bills, actions, status and version links. The project fetches the latest version of each bill itself from the legislature, or from California's bulk download, extracts it, and records the text's source (the export, the fetch or the bulk download), its version label, URL and SHA-256. Scrapers, session lists and bill metadata stay upstream. The bills table is the boundary: ingest maps Open States' fields to the project's own names (`text`, `text_url`, each action's `body`), `lineage text merge` writes each record's chosen text to the `texts` table, and every later stage reads only those two tables. Replacing the source means replacing ingest and the fetch plan; splitting, matching and the evals do not change.

**Consequences.**
- Per-state extraction becomes this project's maintenance. Fixture tests pin each extractor's behavior, and the quality test runs before every full fetch.
- The fetch is a network step outside the pinned snapshot. Its output is pinned the same way: each text's URL, version and SHA-256 are kept, so a rebuild can show what changed.
- Coverage and recall are reported both ways, with the export's text alone and with the fetched text, so the gain is measured rather than assumed.
- Hosts whose robots.txt bars this project, or that do not serve the text, stay disclosed as gaps.

**Result.** What failed upstream was extraction, not the bills: the records were present with their version links, and their text was blank, absent or an amendment. Fetching those versions gives usable text to 147,874 of 151,426 planned records (`reports/text_fetch.json`). Of 447,389 eligible records, Open States' text is usable for 301,442; with the fetched text, 430,900 yield sections, 145,480 of them from fetched text and 2,394 from California's download (`uv run lineage stats` → `reports/coverage.json`, `text_layer`). Commission recall over all 36 enactments rises from 22 to 31. The export-only run is `uv run lineage text merge --exported-only`, then the pipeline through `uv run lineage eval commission --results reports/results_exported_only.json`; the same commands without those options give `reports/results.json`. Eight enactments without exported text are found once their text is fetched, and one in Delaware, whose export stored an amendment in place of the bill, once its text is replaced. Every enactment now has text, so the 5 still missed are lost at the near-duplicate stage: 2 never proposed and 3 at verification ([Commission recall](#commission-recall)).

**Would reverse it.** If a snapshot of the export has usable text for nearly every eligible record, measured the same way, the fetch is retired for those states. If the quality test finds the fetched text no cleaner than the export's where both exist, the project keeps the export's text and discloses the gap. A legislature that asks not to be fetched is removed whatever its robots.txt says.
